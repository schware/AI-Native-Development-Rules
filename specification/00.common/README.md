# Common Specification

## 0. 문서 정보

- 경로: `specification/00.common/README.md`
- 상태: `draft`
- 적용 대상: `01.idea-space`부터 `08.execution`까지의 영역 명세
- 기본 작성 언어: 한국어
- 구조화된 필드명과 값: 영어

> 이 문서는 아직 기준 버전으로 확정되지 않은 초안이다.
>
> 프로젝트가 이 명세의 Git 참조를 적용 대상으로 지정한 경우, 본문의 공식 규칙만 사람과 AI Agent의 실행 기준으로 사용한다.
> `검토 중인 항목`은 공식 규칙으로 사용하지 않는다.
>
> 이 문서는 §11.3의 승격 절차를 거치기 전에 먼저 작성되었다. 현재 작성된 영역 명세는 `07.decision`뿐이므로, `0.x` 버전의 규칙은 둘 이상의 영역에서 검증되지 않은 공통 규칙 후보이다. 다른 영역 명세를 작성할 때 §2.3의 승격 기준을 다시 확인한다.

## 1. 목적과 적용 범위

`00.common`은 여러 영역에서 동일한 의미와 방식으로 사용하는 용어, 원본, 권한, 표현, 식별, 연결, 검증, 보고 및 사람과 AI Agent의 협업 원칙을 정의한다.

이 명세의 목적은 다음과 같다.

- 같은 개념을 영역마다 다르게 정의하는 문제를 방지한다.
- SSoT와 파생 결과를 구분한다.
- 정보의 책임 위치와 Source of Authority를 구분한다.
- 사람과 AI Agent가 기록을 같은 의미로 해석하도록 한다.
- 질문, 판단 및 실행 작업을 성격에 맞는 책임 위치에서 관리한다.
- 기계적으로 판별 가능한 규칙을 자동 검증으로 발전시킬 수 있도록 한다.

적용 영역은 다음과 같다.

```text
01.idea-space
02.problem-space
03.assumptions
04.evidence
05.opportunity
06.vision
07.decision
08.execution
```

이 명세는 프레임워크 저장소와, 프로젝트 설정에서 이 명세를 적용 대상으로 지정한 프로젝트의 사람 및 AI Agent에 적용한다.

`00.common`은 분류하지 못한 규칙이나 문서를 임시로 모아두는 공간으로 사용하지 않는다.

## 2. Common과 영역 명세의 책임

### 2.1 Common의 책임

`00.common`은 다음을 관리한다.

- 공통 용어와 개념
- SSoT, Source of Authority 및 파생 결과의 구분
- 정보별 책임 위치
- 공통 작성 및 표기 원칙
- 공통 식별과 참조 원칙
- 사람과 AI Agent의 기본 권한 경계
- 질문, 판단 및 실행 작업의 책임 위치
- 공통 정의의 승격과 변경 절차
- 공통 검증 원칙

### 2.2 영역 명세의 책임

각 영역 명세는 다음을 관리한다.

- 영역의 목적과 적용 범위
- 기록의 정의, 생성 조건 및 분리 기준
- 영역 고유 필드와 본문 구조
- 상태값, 상태 전환 및 생명주기
- 상태별 필수 정보
- 영역 고유 관계의 의미와 필드
- 관계의 저장 방향(단방향 또는 양방향)
- 양방향 관계의 정방향·역방향 필드 대응
- 자기 참조와 순환 허용 여부
- 고립 기록의 오류·경고 기준
- 위험 평가 대상과 등급 판정 기준
- 위험 등급별 검토 방법
- 영역 고유 역할과 권한
- AI Agent가 수행할 수 있는 작업
- 사람의 확인이 필요한 작업
- 영역 고유 검증 규칙

### 2.3 Common 승격 기준

규칙은 다음 조건을 모두 충족할 때 Common으로 승격한다.

1. 둘 이상의 영역에서 사용한다.
2. 영역이 달라도 의미가 동일하다.
3. 표현 형식과 검증 방법이 동일하다.
4. 변경이 적용 영역 전체에 함께 영향을 주어도 된다.

조건을 충족하지 못하면 해당 영역 명세에 둔다.

### 2.4 충돌 처리

Common과 영역 명세가 충돌하는 것처럼 보이면 문서 위치만으로 우선순위를 판단하지 않고 규칙의 책임 위치를 확인한다.

```text
공통 표기, 식별 및 참조
→ Common

영역의 상태값과 생명주기
→ 영역 명세

영역 고유 관계의 의미와 필드
→ 영역 명세

영역별 위험 판정 기준과 검토 절차
→ 영역 명세
```

실제 충돌이 확인되면 AI Agent는 임의로 해석하지 않는다. 충돌 내용, 책임 위치 및 영향을 기록하고 사람의 판단을 요청한다.

## 3. 용어와 핵심 개념

### 3.1 용어 표기 원칙

- 한국어를 본문의 기본 설명어로 사용한다.
- 영어는 고정 개념명, 역할명, 필드명, 구조화 값, 코드 및 외부 표준에 사용한다.
- SSoT, Source of Authority 및 Provenance는 영어 개념명을 유지하고 한국어로 정의한다.
- 같은 개념에 여러 표현을 혼용하지 않는다.
- `Confirmation`, `Resolution`, `Approval`, `Acceptance`는 서로 다른 행위로 구분한다.
- `MUST`, `SHOULD`, `MAY`, `MUST NOT`은 이번 버전에서 사용하지 않는다. 필수, 금지, 권장 및 선택은 한국어 문장으로 표현한다.

### 3.2 기본 용어

#### 기록 (Record)

영역 명세에 따라 생성되고 관리되는 정보 단위이다.

#### 공식 기록 (Official Record)

영역 명세의 필수 조건과 공통 검증을 통과하여 프로젝트가 지정한 기준 Branch에 반영된 기록이다(§6.1).

공식 기록이라는 것은 기록이 저장소에 반영되었다는 뜻이며, 그 내용이 공식 결론으로 확정되었다는 뜻은 아니다. 결론의 확정 여부는 영역별 상태로 판단한다.

#### 영역 (Area)

특정 종류의 기록과 그 생명주기를 책임지는 명세 단위이다.

#### 명세 (Specification)

기록의 의미, 구조, 상태, 관계, 권한 및 관리 방법을 정의하는 공식 규칙 문서이다.

#### SSoT (Single Source of Truth)

특정 정보를 공식적으로 수정하고 관리하는 하나의 책임 위치이다. 같은 정보가 다른 위치에서 참조될 수는 있지만 여러 위치에서 독립적으로 수정돼서는 안 된다.

#### Source of Authority

특정 정보나 상태를 공식적으로 확정하거나 변경할 권한을 가진 사람, 역할 또는 정책이다. SSoT와 Source of Authority는 서로 다른 개념이다.

#### 파생 결과 (Derived Result)

SSoT를 조회, 집계, 변환, 시각화 또는 요약하여 만든 결과이다. Index, Report, Graph, Dashboard, 검색 결과 및 AI 요약은 파생 결과이며 SSoT를 대신하지 않는다.

#### Provenance

기록이나 결과가 어떤 원본, 작성 주체, 변환, 검토 및 판단 과정을 거쳐 형성됐는지 추적할 수 있는 정보이다.

#### 상태 (State)

기록이 생명주기에서 도달한 현재 단계이다.

#### 생명주기 (Lifecycle)

기록의 생성, 검토, 확정, 보류, 종료 및 대체 과정과 허용된 상태 전환이다.

#### 명세 검토 (Specification Review)

명세의 미확정 규칙을 공식 규칙으로 반영할지 판단하는 활동이다.

#### 기록 검토 (Record Review)

기록의 내용, 근거, 상태, 위험 및 관계를 확인하고 후속 조치를 판단하는 활동이다.

#### 검토 중인 항목 (Open Specification Item)

명세에서 아직 공식 규칙으로 확정되지 않은 후보 또는 질문이다. 실행 기준으로 사용하지 않는다.

#### 충돌 (Conflict)

요청, 원본, 규칙, 관계 또는 권한이 동시에 만족될 수 없는 상태이다.

#### 검증 (Validation)

기록이나 변경이 명세의 형식, 허용값, 참조 및 관계 규칙을 만족하는지 확인하는 활동이다. 의미의 타당성이나 위험 수용을 자동으로 확정하지 않는다.

### 3.3 행위 용어

```text
Confirmation
→ 내용이나 사실을 확인하는 행위

Resolution
→ 미결정 사항에 공식 결론을 내리는 행위

Approval
→ 제안된 변경이나 실행을 허용하는 행위

Acceptance
→ 위험, 제약 또는 결과를 감수하기로 하는 행위
```

한국어 본문에서는 `확인한다`, `결론을 확정한다`, `승인한다`, `위험을 수용한다`처럼 구체적으로 표현한다.

### 3.4 역할 용어

```text
Owner
→ 결과와 지속적인 유지 책임을 가진 역할

Steward
→ 절차, 기록 품질 및 일관성을 관리하는 역할

Reviewer
→ 내용을 검토하고 의견을 제시하는 역할

Approver
→ 제안된 변경이나 실행을 승인하는 역할

Resolver
→ 미결정 사항에 공식 결론을 내리는 역할
```

동일한 사람이 둘 이상의 역할을 맡을 수 있지만 역할의 의미를 합치지는 않는다.

역할별 구체적인 필드명, 필수 여부 및 권한은 해당 영역 명세에서 정의한다.

## 4. 원본, 권한 및 파생 결과

정보별 책임 위치는 다음과 같다.

```text
영역 기록의 내용과 이유
→ 해당 기록

현재 적용되는 공통 규칙
→ 프로젝트가 submodule로 가리키는 버전의 명세 본문(§11.5)

프로젝트 고유의 현재 규칙
→ 프로젝트의 현재 규칙 문서. 규칙마다 근거 결정 ID를 붙인다

프로젝트 단위 메타데이터
→ 저장소 루트의 project.yaml

작업, 담당자, 일정, 우선순위 및 진행 상태
→ 이슈 관리 시스템

파일의 작성자, 변경 시점 및 변경 내용
→ Git

구조화된 단방향 관계
→ 관계를 선언한 기록. 역방향은 계산한다

구조화된 양방향 관계
→ 관계에 참여하는 양쪽 기록이 공동으로 표현

Index, Report, Graph 및 목록
→ 파생 결과
```

파생 결과와 SSoT가 다르면 SSoT를 따른다.

내용을 복사해야 한다면 복사본이 SSoT가 아님을 표시하고 원본 위치를 함께 기록한다.

## 5. 사람과 AI Agent

### 5.1 AI Agent가 수행할 수 있는 일

- 기록 후보와 초안 작성
- 자료 조사와 비교
- 대안과 변경안 제안
- 관련 기록과 근거 탐색
- 형식, 누락, 참조 및 충돌 검사
- 위험 후보와 위험 등급 제안
- 양방향 관계에 참여하는 기록의 동시 수정
- 사람이 승인한 범위의 수정
- 파생 결과와 Graph 생성
- 기계적으로 판별 가능한 검증 수행

### 5.2 AI Agent가 독립적으로 수행할 수 없는 일

AI Agent는 필요한 사람의 승인이나 공식 결정 없이 다음을 수행할 수 없다.

- 사람의 판단이 필요한 상태를 공식적으로 변경
- 위험을 수용한 것으로 기록
- 자신을 사람 Resolver 또는 Approver로 기록
- 확정된 기록의 의미 변경
- 기존 공식 기록의 효력이나 유효성 변경
- 현재 적용 규칙 변경
- 복구하기 어려운 실행
- 권한과 보안 경계 변경

### 5.3 충돌 발견 시 처리

AI Agent는 충돌을 발견하면 다음 순서로 처리한다.

1. 충돌하는 정보와 책임 위치를 확인한다.
2. 범위와 영향을 설명한다.
3. 위험하거나 복구하기 어려운 작업을 중단한다.
4. 충돌하지 않는 조사와 분석은 계속할 수 있다.
5. 필요한 사람의 판단을 요청한다.
6. 판단 결과를 해당 책임 위치에 반영한다.

### 5.4 협업 방식

AI Agent와 함께 일하는 방식은 두 가지이다. 작업마다 사람이 방식을 고르고, 어느 방식이든 결정은 사람이 한다.

| 방식 | 사람이 하는 일 | AI Agent가 하는 일 | 이런 작업에 쓴다 |
|---|---|---|---|
| 설명 후 구현 (기본) | 무엇을 왜 만드는지 설명하고, 결과를 검토한다 | 설명에 맞게 코드를 작성한다 | 대부분의 작업 |
| 직접 작성 | 직접 코드를 작성한다 | 작성하는 방법을 알려 주고, 막히는 곳을 함께 풀어 준다 | 반드시 이해해야 하는 부분 (처음 쓰는 기술, 위험이 큰 부분) |

#### 결과만 요청받았을 때

"만들어 주세요"처럼 방식을 정하지 않고 결과만 요청하면, AI Agent는 설명 후 구현으로 진행한다. 바로 만들지 않고 다음을 먼저 확인한다.

- 무엇을 위해 만드는가 (목적)
- 지켜야 할 조건은 무엇인가
- 사람이 골라야 할 선택이 있는가

#### 선택이 필요할 때

구현 중에 기술이나 구조를 골라야 하면, AI Agent는 멈추고 결정 후보를 제시한다. 사람이 고른 뒤에 구현을 이어간다.

후보마다 다음 세 질문의 답을 함께 적는다.

- 기술적으로 맞는가
- 유지보수가 가능한가
- 10년 뒤에도 괜찮은가

#### 이해가 필요할 때

사람이 직접 작성하지 않은 결과는 AI Agent에게 설명을 요청해서 이해한다. 설명에는 두 가지를 담는다.

- 어떻게 동작하는가
- 왜 그렇게 만들었는가

나중에도 필요한 설명은 결정 이유나 설계 문서에 남긴다.

#### 위험이 클 때

high 위험 작업은 둘 중 하나로 한다.

- 설명 후 구현으로 하되, 독립 AI 검토(§12.3)를 거친다.
- 직접 작성으로 한다.

#### 작성자 표시

결과의 `drafted_by`(§6.7)는 방식에 따라 적는다.

- 직접 작성: `human`
- 설명 후 구현: `ai_agent` (사람이 함께 고쳤으면 `mixed`)

## 6. 공통 표현 원칙

### 6.1 적용 대상 문서

프로젝트는 공식 기록을 인정하는 저장 위치와 반영 조건을 프로젝트 설정에서 정의한다.

이 명세에서 `저장소에 반영`은 프로젝트가 지정한 기준 Branch에 변경이 통합된 상태를 의미한다.

`records/` 아래에서 기준 Branch 반영을 준비하는 기록 후보도 공통 필드를 갖추어야 한다. 영역 명세의 필수 조건과 공통 검증을 통과하여 기준 Branch에 반영된 기록을 공식 기록으로 본다.

`specification/` 아래의 명세 문서와 `reports/` 아래의 파생 결과에는 공통 기록 필드를 강제하지 않는다. 명세 문서와 보고서는 각 문서 유형의 메타데이터 규칙을 따른다.

### 6.2 YAML과 Markdown

구조화된 메타데이터가 필요한 Markdown 기록은 하나의 파일 안에서 YAML 메타데이터와 Markdown 본문을 함께 관리한다.

```text
YAML
→ 식별, 상태, 시점, 책임 및 구조화된 관계

Markdown
→ 배경, 설명, 분석, 근거, 이유, 영향 및 질문
```

같은 기록을 위한 YAML 파일과 Markdown 파일을 별도로 관리하지 않는다.

외부 원자료나 비 Markdown 기록의 관리 방법은 해당 영역 명세에서 정한다.

### 6.3 필드와 구조화 값

- YAML 필드명은 영어 `snake_case`를 사용한다.
- 상태, 등급 및 유형처럼 기계가 판별하는 값은 영어로 작성한다.
- 제목과 본문은 프로젝트 기본 언어를 사용한다.
- 같은 의미의 필드명이나 구조화 값을 여러 표기로 혼용하지 않는다.

### 6.4 프로젝트 메타데이터

저장소 루트의 `project.yaml`은 프로젝트 단위 정보의 SSoT이다.

```yaml
project_id: EXAMPLE001
project_name: "Example Project"
default_language: ko

common_spec:
  repository: "<repository-url>"
  path: "specification/00.common/README.md"
  git_ref: "<tag-or-commit>"

area_specs:
  decision:
    path: "specification/07.decision/README.md"
    git_ref: "<tag-or-commit>"

repository:
  base_branch: main

records:
  decision: "records/07.decision"

identifiers:
  person: "<person-id-rule>"
  issue_patterns:
    - "<issue-id-regex>"

roles:
  PL:
    - "<person-id>"

reports:
  path: "reports"
  types: []
```

```text
project_id, project_name, default_language
→ 프로젝트의 식별자, 표시 이름 및 기본 작성 언어

common_spec
→ Common의 저장소, 경로 및 버전(§11.4, §11.5). path는 기준 저장소 안의 경로이다. git_ref는 submodule이 가리키는 Tag와 같아야 한다. 기준 저장소 자신은 repository를 생략할 수 있다

area_specs
→ 영역 명세의 경로와 버전. 키는 영역 이름이다. 사용하는 영역만 적는다

repository.base_branch
→ 공식 기록의 반영 기준 Branch(§6.1)

records
→ 영역별 공식 기록의 저장 경로(§6.8). 키는 area_specs와 같은 영역 이름을 쓴다

identifiers
→ 사람 식별자 규칙과 이슈 식별자 형식

roles
→ 역할과 그 역할을 맡은 사람의 대응. 한 사람이 여러 역할을 맡을 수 있다(§3.4)

reports
→ 보존하는 보고서의 저장 경로와 보고 유형(§10.1). 보고서를 보존하지 않으면 생략한다
```

공식 기록의 저장 위치는 `records`이고, 반영 조건은 `repository.base_branch`에 통합되는 것이다(§6.1).

`project_id`와 `project_name`은 개별 기록에 반복하지 않는다.

여러 이슈 관리 시스템을 사용하는 경우에는 `issue_patterns`만으로 시스템을 구분할 수 있도록 형식을 정의한다.

### 6.5 공통 YAML 필드

모든 공식 기록은 다음 필드를 가진다.

```yaml
---
id: EXAMPLE001-A001
title: "기록 제목"
status: "<area-defined-status>"
created_at: "2026-10-22"
drafted_by: human
issues: []
---
```

```text
id
→ 기록의 고유 ID

title
→ 기록 제목

status
→ 현재 상태. 상태 생명주기가 없으면 not_applicable

created_at
→ 기록을 논리적으로 생성한 날짜

drafted_by
→ human, ai_agent, mixed 중 하나

issues
→ 연결된 실행 이슈 목록. 없으면 []
```

### 6.6 날짜와 빈 값

Git의 최초 Commit 시각은 파일이 저장소 이력에 들어간 시점이며 `created_at`과 다를 수 있다.

```text
날짜
→ YYYY-MM-DD 문자열

시간 포함
→ ISO 8601 문자열

빈 목록
→ []

선택 단일값
→ 필드 생략

필수 단일값 누락
→ 검증 실패
```

### 6.7 AI 작성 내용과 사람 확인

`drafted_by`는 현재 기록의 의미 있는 내용을 작성한 주체를 요약하여 나타낸다. 상세 작성자와 변경 이력은 Git을 기준으로 확인한다.

```text
human
→ 사람이 작성함

ai_agent
→ AI Agent가 작성함

mixed
→ 사람과 AI Agent가 함께 작성함
```

`drafted_by`가 `ai_agent` 또는 `mixed`이고 사람이 내용을 확인한 경우 다음을 기록한다.

```yaml
confirmed_by: "person-id"
confirmed_at: "2026-10-22"
```

사람 확인 전에는 `confirmed_by`와 `confirmed_at`을 생략한다.

`confirmed_by`는 사람이 AI 작성 내용을 공식 기록에 포함할 수 있다고 판단했음을 나타낸다. 사실성, 공식 결론, 변경 승인 또는 위험 수용을 대신하지 않는다.

`confirmed_by`의 식별자 형식은 프로젝트의 사용자 식별 규칙을 따른다.

오탈자, 공백, 링크 및 의미를 바꾸지 않는 수정은 기존 확인 상태를 유지한다.

결론, 이유, 근거, 위험, 영향, 상태 전환 조건 또는 관계가 변경되면 기존 확인 정보를 제거하고 다시 확인한다. 변경에 사람과 AI Agent가 함께 참여했다면 `drafted_by`를 `mixed`로 갱신한다.

### 6.8 저장 경로와 파일 형식

```text
specification/
→ 명세

records/
→ 공식 기록

reports/
→ 보존하기로 한 파생 보고서
```

공식 기록은 `records/` 아래에서 영역별로 구분한다.

구체적인 하위 경로와 영역의 매핑은 프로젝트 설정(§6.4의 `records`)에서 명시한다.

텍스트 파일은 UTF-8과 LF를 사용한다.

```gitattributes
*.md text eol=lf
*.yaml text eol=lf
*.yml text eol=lf
*.json text eol=lf
```

## 7. 식별과 참조

### 7.1 프로젝트 ID

프로젝트 ID는 영문 대문자 3~8자와 숫자 3자리로 구성한다.

```regex
^[A-Z]{3,8}[0-9]{3}$
```

프로젝트 ID는 관리 범위 안에서 고유해야 한다. 공식 기록에서 사용된 이후에는 프로젝트 이름이 변경돼도 바꾸거나 재사용하지 않는다.

### 7.2 기록 ID

```text
{project_id}-{record_type}{sequence}
```

```text
idea-space     → I
problem-space  → P
assumptions    → A
evidence       → E
opportunity    → O
vision         → V
decision       → D
```

파일 기반 기록을 사용하지 않는 영역에는 기록 유형 코드를 부여하지 않는다. 기록 방식이 변경되면 해당 영역의 유형 코드도 별도 규칙으로 정의한다.

### 7.3 일련번호

- 프로젝트와 기록 유형별로 독립적으로 증가한다.
- 최소 세 자리로 쓴다.
- 생성 시점에 확인한 다음 미사용 번호를 후보로 부여한다.
- 기준 Branch 반영 전에 ID 중복을 다시 확인한다.
- 한 번 저장소에 반영된 ID는 재사용하지 않는다.
- 999를 넘으면 자릿수를 늘린다.

```text
A001
A999
A1000
```

### 7.4 변경과 재사용

다른 기록, 이슈 또는 Git 변경에서 참조된 ID는 변경하거나 재사용하지 않는다.

아직 참조되지 않았고 저장소에 반영되기 전에 생성 오류가 발견된 경우에는 수정할 수 있다.

### 7.5 파일 이름과 이전 ID

Markdown 기록 파일 이름은 ID와 일치시킨다.

```text
EXAMPLE001-A001.md
```

제목, 상태, 날짜 및 작성자는 파일 이름에 포함하지 않는다.

마이그레이션한 기록은 이전 ID를 목록으로 보존한다.

```yaml
legacy_ids:
  - OLD-A-022
```

### 7.6 중복 확인

새 기록을 생성하거나 Git 변경을 통합하기 전에 ID 중복 여부를 확인한다. 초기에는 수동으로 확인하고 이후 CI에서 차단한다.

## 8. 관계, Graph, Git 및 이슈 관리

### 8.1 관계의 저장 방향

구조화된 관계를 사용하는 영역 명세는 관계마다 저장 방향을 단방향 또는 양방향 중에서 정한다.

```text
단방향
→ 관계를 선언하는 한쪽 기록에만 저장하고 역방향은 계산한다

양방향
→ 관계에 참여하는 양쪽 기록에 모두 저장한다
```

저장 방향을 정하지 않은 관계는 구조화된 관계로 사용하지 않는다.

#### 단방향 관계

관계는 영역 명세가 지정한 쪽의 기록에만 저장한다. 반대쪽 기록에는 역방향 필드를 저장하지 않는다.

역방향 관계가 필요하면 선언된 관계를 기준으로 계산한다. 기록의 `issues`와 이슈 관리 시스템의 역방향 연결(§8.4)도 같은 방식이다.

#### 양방향 관계

관계를 추가, 변경 또는 제거할 때는 양쪽 기록을 하나의 변경 단위로 수정하고, Git에 반영할 때 같은 Commit 또는 Pull Request에 포함한다.

양방향 관계는 동일한 정보를 독립적으로 관리하는 두 개의 SSoT가 아니다.

양쪽 기록의 대응 필드는 하나의 논리적 관계를 공동으로 구성하며, 양쪽 값이 일치할 때만 해당 관계를 유효한 공식 관계로 인정한다.

한쪽 관계가 누락되거나 양쪽 값이 일치하지 않으면 어느 한쪽을 자동으로 우선하지 않고 관계 무결성 오류로 처리한다.

관계의 저장 방향, 양방향 관계의 필드 대응 및 순환 허용 여부는 해당 관계를 사용하는 영역 명세에서 정의한다.

### 8.2 AI Agent의 관계 변경

AI Agent는 관계 변경 시 다음을 확인한다.

- 참조한 기록이 존재하는가
- 관계 대상의 기록 유형이 허용되는가
- 관계가 중복되지 않았는가
- 단방향 관계를 지정된 쪽에만 저장했는가
- 양방향 관계라면 양쪽 기록을 모두 수정했고, 정방향과 역방향 필드가 대응하는가

관계 의도가 불명확하거나 양쪽 기록이 충돌하면 임의로 복구하지 않고 사람의 판단을 요청한다.

### 8.3 Graph 검증

Graph는 관계를 조회하고 검증하는 파생 결과이다. 관계의 SSoT로 사용하거나 Graph에서 관계를 직접 수정하지 않는다.

Graph는 다음을 점검한다.

- 양방향 관계의 역방향 누락
- 양방향 관계의 양쪽 불일치
- 단방향 관계의 반대쪽에 저장된 역방향 필드
- 존재하지 않는 기록 참조
- 허용되지 않은 기록 유형 간 관계
- 자기 자신 참조
- 금지된 순환
- 중복 관계
- 고립된 기록

양방향 관계의 누락과 불일치는 오류로 처리한다. 고립 기록은 영역 규칙에 따라 오류 또는 경고로 처리한다.

Graph는 사람이 요청하거나 관계 변경을 검토할 때 SSoT에서 생성한다.

보고서의 Graph 스냅샷은 과거 검토 자료로 보존할 수 있지만 현재 관계의 SSoT가 아니다.

### 8.4 이슈 관리 시스템과의 연결

`이슈 관리 시스템`은 작업, 담당자, 일정, 우선순위, 진행 상태 및 완료 여부를 관리하는 외부 시스템의 공통 명칭이다. 특정 제품명은 Common 용어로 사용하지 않는다.

기록과 실행 이슈의 연결은 기록의 `issues`에서 관리한다. `issues`는 연결 정보의 SSoT이다. 이슈 관리 시스템을 사용하지 않거나 연결된 이슈가 없으면 빈 목록을 사용한다.

```yaml
issues:
  - PROJ-101
```

이슈의 상태, 담당자, 일정, 우선순위 및 완료 여부는 이슈 관리 시스템에서 관리한다. 이러한 실행 정보는 기록에 복제하지 않는다.

이슈 관리 시스템에서 기록으로 향하는 역방향 연결은 기록의 `issues`를 기준으로 계산한다. 외부 시스템이 역방향 링크 저장을 지원하고 AI Agent에 필요한 권한과 승인 범위가 있으면 같은 값을 동기화할 수 있다.

AI Agent는 `issues`에 선언된 연결의 의미를 변경하지 않는 범위에서 다음 작업을 자동으로 수행할 수 있다.

- 연결된 이슈의 존재 여부 확인
- 외부 시스템이 지원하는 경우 누락된 역방향 링크 추가
- 이슈 ID 형식 검증
- 역방향 링크의 중복 제거
- 역방향 연결 목록 정렬
- Graph 재검증

기존 연결 삭제, 다른 기록으로의 이동, 이슈 분할·병합, 존재하지 않는 ID 제거 및 충돌 해결은 사람의 확인 후 반영한다.

동기화에 실패하면 기록의 `issues`를 기준으로 불일치를 보고한다. AI Agent는 외부 시스템의 기존 연결을 임의로 삭제하거나 변경하지 않는다.

### 8.5 Git과 Record-Refs

공식 기록을 생성하거나 의미 있게 변경하는 커밋과 공식 기록에 따라 코드, 설정 또는 명세를 변경하는 커밋은 `Record-Refs` Git trailer를 사용한다.

```text
Record-Refs: EXAMPLE001-A001
```

복수 기록은 쉼표로 구분한다.

```text
Record-Refs: EXAMPLE001-A001, EXAMPLE001-E009
```

결론, 이유, 근거, 상태, 위험, 관계, 명세 규칙, 코드 동작 또는 설정 의미를 변경하면 의미 있는 변경으로 본다.

오탈자, 공백, 단순 링크 및 의미를 바꾸지 않는 수정에는 생략할 수 있다.

Squash Merge를 사용하면 최종 Squash Commit 메시지에 `Record-Refs`를 유지한다.

`Record-Refs`는 Pull Request 검토 또는 기준 Branch 반영 전에 확인한다. 자동 검증 도구가 없는 경우에는 사람이 Commit 메시지와 관련 기록을 확인한다.

필수 `Record-Refs`가 없거나 참조 ID가 존재하지 않으면 기준 Branch 반영 전에 수정한다.

### 8.6 삭제·철회·이동

- 외부에서 참조된 공식 기록은 물리적으로 삭제하지 않는다.
- 아직 저장소에 반영되거나 참조되지 않은 잘못된 초안은 삭제할 수 있다.
- 철회와 종료 상태는 영역별 생명주기에서 정의한다.
- 공통 `withdrawn` 상태는 두지 않는다.
- 파일을 이동해도 ID는 변경하지 않는다.
- 경로보다 ID 참조를 우선한다.

## 9. 상태와 위험

### 9.1 상태

모든 공식 기록은 `status`를 가진다.

상태값과 전환은 영역별 명세에서 정의한다.

상태 생명주기를 사용하지 않는 영역은 다음 값을 사용한다.

```yaml
status: not_applicable
```

공통 상태 범주와 공통 종료 상태는 도입하지 않는다.

### 9.2 위험 등급

위험을 구조화하는 영역은 다음 값을 사용한다.

```text
low
medium
high
```

```text
low
→ 영향이 제한적이고 쉽게 복구할 수 있음

medium
→ 일부 기록이나 작업에 영향을 주며 별도 검토가 필요함

high
→ 영향 범위가 크거나 복구가 어렵고 사람의 명시적인 판단이 필요함
```

`risk_level`은 모든 기록에 강제하지 않는다.

### 9.3 영역별 위험 정의

위험을 사용하는 영역은 다음을 영역 명세에서 정의한다.

- 위험 평가 대상
- 등급별 판정 기준
- 등급별 검토 방법
- 위험 등급 변경 조건
- 최종 판단에 필요한 역할과 행위

새로운 근거, 영향 범위 또는 복구 가능성이 확인되면 개별 기록의 위험 등급을 변경할 수 있다.

검토 절차를 줄이기 위해 위험 등급을 낮춰서는 안 된다.

AI Agent는 위험 등급을 제안하거나 재평가할 수 있지만 위험을 최종적으로 수용할 수 없다.

## 10. 보고서와 기록 검토

### 10.1 보고서 생성

보고서는 사람이 요청할 때 생성한다. 정기 자동 생성은 현재 도입하지 않는다.

`report_type`과 대상 기간의 표현은 프로젝트 설정(§6.4의 `reports`)에서 정의한다. 보고 유형은 자동 생성 주기를 의미하지 않는다.

사람 또는 AI Agent가 보고서를 생성할 수 있다. 사람이 보존을 요청한 보고서는 `reports/`에 저장할 수 있다.

### 10.2 보고서 원칙

보고서는 특정 시점이나 기간의 상태, 변경, 이상 징후 및 검토 대상을 SSoT에서 수집한 파생 결과이다.

- 원본의 ID 또는 위치를 연결한다.
- 생성 시점과 대상 범위를 표시한다.
- 기준 Git Commit을 표시한다.
- 원본에 없는 내용을 확정된 사실처럼 추가하지 않는다.
- 공식 상태나 규칙을 보고서에서 변경하지 않는다.

AI Agent는 보고서를 원본과 검토 대상을 찾는 보조 자료로 사용할 수 있지만 보고서만으로 현재 상태를 확정하거나 실행하지 않는다.

### 10.3 보고서 메타데이터

```yaml
---
report_type: "<project-defined-type>"
scope: "<target-range>"
generated_at: "2026-10-22T11:32:00+09:00"
base_commit: "<full-commit-hash>"
generated_by: ai_agent
generator: ai_tool
---
```

`generated_by`는 `human`, `ai_agent`, `mixed` 중 하나이다.

`base_commit`은 보고서를 생성할 때 조회한 기준 Branch의 전체 Commit 해시를 기록한다.

### 10.4 기록 검토 결과의 책임 위치

```text
새로운 판단
→ 판단의 성격을 책임지는 영역

기존 기록 수정
→ 해당 기록

현재 규칙 변경
→ 사람의 공식 결정 후 해당 명세

실행 작업
→ 이슈 관리 시스템

새로운 정보
→ 성격에 맞는 영역
```

### 10.5 프레임워크 효과 지표

평가를 요청한 경우 다음 지표를 사용할 수 있다.

```text
rework_count
inconsistency_count
review_lead_time
governance_overhead
```

정기 측정은 강제하지 않는다.

## 11. 명세 관리와 Common 승격

### 11.1 질문과 작업의 책임 위치

```text
특정 기록의 미해결 질문
→ 해당 기록

명세 규칙의 미확정 사항
→ 해당 명세의 검토 중인 항목

조사, 수정 및 자동화 작업
→ 이슈 관리 시스템

사람의 공식 판단이 필요한 새로운 결론
→ 판단의 성격을 책임지는 영역의 후보

대화에서 발견한 지속적 정보
→ 성격에 맞는 책임 위치
```

### 11.2 명세 규칙의 확정

```text
선택지와 영향 분석
→ 위험 확인
→ 사람의 명시적인 결정
→ 명세 본문과 예시 수정
→ 관련 명세의 정합성 확인
→ 검토 중인 항목에서 제거
→ Git 변경 이력으로 보존
```

### 11.3 Common 승격

1. 하나의 영역에서 후보를 정의한다.
2. 실제 적용으로 의미와 구조를 검증한다.
3. 다른 영역에서도 동일한 필요를 확인한다.
4. 의미, 형식 및 검증 조건을 비교한다.
5. 사람이 공통 적용 여부를 결정한다.
6. Common에 반영한다.
7. 영역의 중복 정의를 Common 참조로 바꾼다.
8. 영향을 받는 영역의 정합성을 확인한다.

### 11.4 명세 버전

기준 버전과 변경 버전은 Semantic Versioning 형식의 Git Tag로 식별한다. 기준 버전으로 확정되지 않은 후보는 Git Commit으로 식별할 수 있다.

```text
0.x.x
→ 실험 및 초안

1.0.0
→ 첫 기준 버전

PATCH
→ 의미를 바꾸지 않는 수정

MINOR
→ 하위 호환 가능한 추가

MAJOR
→ 마이그레이션이 필요한 비호환 변경
```

프로젝트는 `project.yaml`에 적용할 Common의 경로와 Git Tag 또는 Commit을 기록한다.

재현 가능한 적용을 위해 이동 가능한 Branch 이름보다 Git Tag 또는 전체 Commit 해시를 사용한다.

### 11.5 다른 프로젝트의 Common 적용

다른 프로젝트는 이 저장소를 Git submodule로 연결하고, 특정 버전(Git Tag)을 가리킨다. 공통 규칙은 이 저장소에서만 고치고, 프로젝트는 확인한 뒤 가리키는 버전을 옮긴다.

```text
기준 저장소 (규칙은 여기서만 고친다)
   v0.2 ──→ v0.3 ──→ v0.4
     ↑ submodule이 가리키는 버전
프로젝트 A: v0.2를 가리키며 진행 → 확인 후 v0.3으로 옮김
프로젝트 B: v0.2를 계속 가리킴 (옮기지 않기로 결정)
```

#### 연결과 기준 버전

- 프로젝트는 이 저장소를 submodule로 연결하고, submodule이 Git Tag를 가리키도록 한다.
- submodule이 가리키는 버전이 프로젝트가 따르는 버전이다. `project.yaml`의 `git_ref`에는 같은 Tag를 기록하고, 둘을 함께 바꾼다(§6.4).
- 프로젝트는 submodule 안의 파일을 고치지 않는다.

#### 프로젝트 고유의 규칙

- 공통 규칙에 없는, 그 프로젝트에만 적용하는 규칙은 프로젝트의 현재 규칙 문서에 둔다(§4).
- 프로젝트 고유의 규칙을 정하거나 바꿀 때는 프로젝트의 결정 기록으로 남기고, 현재 규칙 문서의 해당 규칙에 그 결정 ID를 붙인다.
- 프로젝트 고유의 규칙은 공통 규칙과 충돌하지 않게 둔다. 충돌하면 §5.3에 따라 사람의 판단을 요청한다.

#### 공통 규칙을 바꾸고 싶을 때

- 프로젝트에서 공통 규칙을 바꿀 필요를 발견하면, 사람이 이 저장소에 반영을 요청한다. 근거가 된 프로젝트의 결정 기록을 함께 참조한다.
- 이 저장소에서 규칙을 고친 뒤 새 버전(Git Tag)을 만든다.
- AI Agent는 사람의 요청 없이 이 저장소의 규칙을 고치지 않는다(§5.2).

#### 새 버전으로 옮길 때

- 프로젝트는 새 버전의 변경 내용을 확인하고, 옮길지 사람이 결정한다. 결정은 프로젝트의 결정 기록으로 남긴다.
- 옮기지 않으면 기존 버전을 계속 가리킨다.
- 옮기면 submodule이 새 Tag를 가리키게 하고 `git_ref`를 같은 Tag로 바꾼 뒤, 바뀐 규칙이 프로젝트의 기존 기록과 현재 규칙 문서에 영향을 주는지 확인한다.

### 11.6 기준 버전 조건

Common은 다음 조건을 충족할 때 기준 버전으로 확정할 수 있다.

- 본문 규칙 사이에 모순이 없다.
- 같은 용어가 문서 전체에서 같은 의미로 사용된다.
- 규칙과 예시가 일치한다.
- 사람과 AI Agent의 책임이 구분된다.
- SSoT와 Source of Authority가 구분된다.
- SSoT와 파생 결과가 구분된다.
- Common과 영역 명세의 책임이 구분된다.
- 영역 명세가 공통 규칙을 중복 정의하지 않고 Common을 참조한다.
- 구조화된 관계를 사용하는 영역이 관계마다 저장 방향과 순환 규칙을 정의하고, 양방향 관계라면 필드 대응을 정의한다.
- 프로젝트가 공식 기록의 저장 위치, 반영 조건 및 기준 Branch를 정의한다.
- ID 중복과 양방향 관계 불일치를 기준 Branch 반영 전에 확인할 수 있다.
- 자동 검증과 사람 판단의 범위가 구분된다.
- 검토 중인 항목이 공식 규칙과 구분된다.
- 남은 미확정 사항이 기본 운영을 방해하지 않는다.

기준 버전 이후 공통 규칙의 의미를 변경할 때는 영향을 받는 영역, 기존 기록, 자동 검증 및 적용 프로젝트를 확인하고 공식 판단의 근거를 남긴다.

## 12. 공통 검증과 독립 AI 검토

### 12.1 공통 검증

```text
수동 체크리스트
→ AI Agent 검사
→ 검증 스크립트
→ CI
→ Agent Harness의 실행 전 검사
```

검증 범위는 다음과 같다.

- 프로젝트 ID와 기록 ID
- ID 중복
- 파일 이름과 내부 ID
- 공통 필드와 값 형식
- `status` 허용값
- 참조 대상 존재 여부
- 양방향 관계의 누락과 불일치
- 단방향 관계의 역방향 필드 저장
- 관계 유형과 금지된 순환
- Git 변경과 `Record-Refs`
- 파일 인코딩과 줄바꿈

의미, 가치, 근거의 충분성 및 위험 수용은 자동 검증으로 판정하지 않는다.

### 12.2 AI Agent의 명세 사용

AI Agent는 작업 전에 다음을 확인한다.

1. 프로젝트가 submodule로 가리키는 버전의 Common 규칙(§11.5)
2. 대상 영역 명세
3. 프로젝트의 현재 적용 규칙
4. 관련 기록과 SSoT
5. 작업 범위와 권한

검토 중인 항목은 실행 기준으로 사용하지 않는다.

용어 또는 규칙 충돌을 발견하면 임의로 병합하거나 해석하지 않고 사람에게 보고한다.

### 12.3 독립 AI 검토 적용 범위

독립 AI 검토는 작성 대화와 분리된 새로운 AI 세션에서 수행한다.

다음 변경은 독립 AI 검토를 수행한다.

- `high` 위험 변경
- Common의 의미 변경
- 영역 명세의 핵심 개념 또는 생명주기 변경
- SSoT 또는 Source of Authority 변경
- ID, 관계 또는 상태 구조 변경
- 기존 공식 기록의 효력이나 유효성을 변경하는 작업
- 여러 기록에 영향을 주는 일괄 변경
- 복구하기 어렵거나 영향 범위가 불명확한 변경
- 영역 명세가 독립 AI 검토를 요구하는 변경

그 밖의 변경도 사람이 필요하다고 판단하면 추가 요청할 수 있다.

오탈자, 공백, 단순 링크 및 의미를 바꾸지 않는 수정에는 기본적으로 요구하지 않는다.

### 12.4 독립 AI 검토 입력과 결과

입력:

- 변경 전후 차이
- 변경된 파일
- 관련 기록과 SSoT
- 적용 Common 및 영역 명세
- 검토 기준

작성 과정의 전체 대화는 반드시 필요한 경우가 아니면 제공하지 않는다.

결과:

```text
Blocking
→ 반영 전에 해결해야 하는 문제

Warning
→ 사람이 확인해야 하는 위험

Suggestion
→ 선택적 개선

No Issue
→ 확인했으나 문제가 없는 주요 항목
```

독립 AI 검토는 사람의 기록 검토, 공식 결정, 승인 또는 위험 수용을 대신하지 않는다.

독립 AI 검토가 요구되지만 수행할 수 없는 경우에는 사유를 기록하고 사람의 별도 검토로 대체한다. 독립 AI 검토의 실패나 부재를 이유로 사람의 최종 판단을 생략할 수 없다.

## 13. 검토 중인 항목

- 공통 규칙 후보의 검증: §0에 적은 대로, 다른 영역 명세를 작성하면서 각 규칙이 §2.3의 승격 기준을 충족하는지 확인한다.

이 밖에 실제 프로젝트 적용과 기준 버전 조건 확인이 남아 있다.

새로운 미확정 사항이 발견되면 책임 위치를 확인한 후 Common, 해당 영역 명세, 프로젝트 설정 또는 이슈 관리 시스템으로 분류한다.
