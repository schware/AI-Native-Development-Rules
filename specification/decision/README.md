# Decision Specification 초안

## 1. 목적

이 문서는 AI Agent를 활용한 개발에서 제안되거나 검토된 내용과 사람이 최종적으로 확정한 결정을 구분하고, 이를 기록하고 관리하는 방법을 명세한다.

결정 당시의 배경, 검토한 대안, 판단 이유 및 영향을 기록하여 이후에도 결정의 의미와 변경 이력을 이해하고 추적할 수 있도록 한다.

결정안의 제안, 분석 및 검토에는 사람과 AI Agent가 참여할 수 있으며, 결정의 최종 확정은 사람이 수행한다.

## 2. 결정의 정의

결정은 검토한 문제와 대안에 대해 사람이 책임을 가지고 확정한 결론이다.

팀 프로젝트에서 결정은 개인의 생각이나 비공식적인 합의에 머무르지 않고, 관련된 구성원이 그 의미와 적용 범위를 확인할 수 있도록 기록되어야 한다.

대화에서 언급되거나 문서에 작성되었다는 사실만으로 해당 내용이 자동으로 결정이 되는 것은 아니다.

```text
AI Agent가 제안한 내용 ≠ 확정된 결정
대화에서 논의한 내용 ≠ 확정된 결정
문서에 작성된 내용 ≠ 현재 적용되는 규칙
사람이 검토하고 확정한 내용 = 결정
```

결정은 현재 적용되는 규칙이나 실행 가능한 작업으로 이어질 수 있지만, 결정 기록 자체가 항상 현재 규칙이나 실행 작업을 대신하는 것은 아니다.

## 3. 결정 기록이 필요한 이유

사람과 AI Agent가 대화 중심으로 작업하면 질문, 제안, 가정, 근거, 결정 및 후속 작업이 하나의 대화 안에 섞일 수 있다.

대화만으로는 검토 중인 내용과 확정된 결정의 경계를 지속적으로 유지하기 어렵다. 결정의 범위와 상태가 기록되지 않으면 사람과 AI Agent가 동일한 내용을 서로 다르게 이해하거나, 검토 중인 내용을 현재의 실행 기준으로 잘못 적용할 수 있다.

팀 프로젝트에서는 여러 구성원이 서로 다른 대화와 작업 환경에서 업무를 진행할 수 있다. 따라서 결정의 내용뿐 아니라 상태, 적용 범위, 책임 및 변경 사항도 일관되게 전달되어야 한다.

### 3.1 결정의 구분과 해석

- 사람과 AI Agent의 제안이나 검토 중인 내용이 확정된 결정으로 잘못 기록될 수 있다.
- 검토 중인 결정, 확정된 결정, 과거 결정 및 현재 유효한 결정을 구분하기 어려울 수 있다.
- 결정 이유에 새로운 결정, 검증되지 않은 가정 또는 미해결 질문이 섞일 수 있다.
- 결정 당시 검토한 대안과 판단 이유를 찾기 어려울 수 있다.
- AI Agent가 제안이나 과거 결정을 현재 실행 기준으로 잘못 해석할 수 있다.

### 3.2 팀의 협업과 책임

- 구성원마다 결정의 의미와 적용 범위를 다르게 이해할 수 있다.
- 누가 결정안을 제안하고 검토했으며, 누가 최종적으로 확정하고 책임지는지 확인하기 어려울 수 있다.
- 회의나 개별 대화에서 이루어진 결정이 공식 기록에 반영되지 않을 수 있다.
- 결정의 변경 사항이 문서, 이슈, 코드 및 AI Agent의 작업 기준에 일관되게 반영되지 않을 수 있다.
- 여러 구성원이 같은 기록을 동시에 작성하거나 수정하면서 충돌과 누락이 발생할 수 있다.
- 담당자나 팀 구성이 변경되면 결정 당시의 맥락과 판단 이유가 전달되지 않을 수 있다.

이러한 문제로 인해 사람, 대화, 작업 환경 또는 AI Agent가 변경되면 이전 작업의 맥락을 이어가기 어려울 수 있다.

## 4. 결정 기록 단위

결정 하나당 하나의 Markdown 파일로 기록한다.

하나의 결정 파일은 하나의 독립된 판단 단위를 기록한다. 여러 결정을 하나의 파일에 모아 기록하지 않는다.

이를 통해 결정별 변경 이력을 독립적으로 관리하고, 특정 결정을 이슈나 git 변경 이력에서 직접 참조할 수 있도록 한다.

### 4.1 결정의 분리 기준

결론이 독립적으로 검토되거나 변경될 수 있다면 별도의 결정으로 분리한다.

분리 여부는 다음 질문으로 판단한다.

- 해결하려는 문제가 서로 다른가
- 검토한 대안과 판단 이유가 서로 다른가
- 별도의 위험 검토나 책임 범위가 필요한가
- 하나의 결론이 변경되어도 다른 결론은 계속 유효한가
- 적용 대상, 범위, 조건 또는 유효 기간이 서로 다른가

관련 정보나 자료 자체는 독립된 결정이 아니다. 다만 이를 검토하는 과정에서 별도의 판단과 확정이 필요해지면 새로운 결정으로 분리한다.

문서의 길이나 관련 자료의 수가 아니라 판단의 독립성을 기준으로 결정을 분리한다.

## 5. 결정 ID와 파일 이름

각 결정에는 프로젝트와 개별 결정을 식별할 수 있는 고유한 ID를 부여한다.

결정 ID는 제목이나 상태가 변경되더라도 동일한 결정을 일관되게 식별하고, 문서·이슈·git 변경 이력에서 공통으로 참조하기 위해 사용한다.

### 5.1 결정 ID의 구성

현재 검토 중인 결정 ID 형식은 다음과 같다.

```text
{project_id}-D{sequence}
```

- `project_id`: 프로젝트를 구분하는 고정 식별자
- `D`: 결정을 나타내는 유형 문자
- `sequence`: 프로젝트 안에서 결정 파일을 생성할 때 부여하는 일련번호

형식 예시는 다음과 같다.

```text
JPS001-D001
TDS001-D001
```

예시에 사용된 프로젝트 ID, 유형 문자 및 일련번호 자릿수는 최종 규칙이 아니다.

### 5.2 프로젝트 이름과 프로젝트 ID

프로젝트 이름은 사람이 프로젝트를 식별하기 위한 표시 이름이며, 프로젝트 ID는 관련 기록에서 프로젝트를 일관되게 식별하기 위한 고정값이다.

```text
프로젝트 이름: Java-POSSERVER
프로젝트 ID: JPS001
```

프로젝트 이름이 변경되더라도 이미 부여한 프로젝트 ID는 변경하지 않는 것을 기본 원칙으로 한다.

프로젝트 내부의 애플리케이션이나 모듈은 기본적으로 해당 프로젝트 ID를 사용한다. 독립적인 개발 및 결정 관리 단위로 분리되는 경우에는 별도의 프로젝트 ID를 부여할 수 있다.

프로젝트 ID의 생성과 발급 방법은 별도로 검토한다.

### 5.3 결정 일련번호

결정 일련번호는 프로젝트별로 독립적으로 부여한다.

```text
JPS001-D001
JPS001-D002
JPS001-D003
```

일련번호는 결정 파일을 생성할 때 부여하며, 해당 프로젝트에서 아직 사용하지 않은 다음 번호를 사용한다. 이미 사용한 일련번호는 재사용하지 않는다.

### 5.4 파일 이름

결정 파일의 이름은 결정 ID와 일치시킨다.

```text
결정 ID: JPS001-D001
파일 이름: JPS001-D001.md
```

제목, 상태, 위험 등급 및 날짜는 파일 이름에 포함하지 않는다. 제목이나 상태가 변경되더라도 결정 ID와 파일 이름은 유지한다.

사용:

```text
JPS001-D001.md
```

사용하지 않음:

```text
JPS001-D001-decision-record-format.md
JPS001-D001-decided.md
JPS001-D001-2026-10-21.md
```

### 5.5 결정 ID와 파일 이름의 일치

결정 파일의 이름과 파일 내부에 기록된 결정 ID는 동일해야 한다.

```text
파일 이름: JPS001-D001.md
결정 ID: JPS001-D001
```

두 값이 일치하지 않으면 유효한 결정 기록으로 처리하지 않는다. 불일치를 발견하면 프로젝트 ID, 결정 유형 및 일련번호를 확인하여 수정한다.

### 5.6 결정 ID의 변경과 재사용

결정 ID는 생성 이후 변경하거나 재사용하지 않는다.

결정 기록이 `rejected` 또는 `superseded` 상태가 되더라도 기존 ID와 파일을 유지한다. 결정 ID가 다른 문서, 이슈 또는 git 변경 이력에서 참조된 경우에도 변경하거나 재사용하지 않는다.

다만 다른 기록에서 아직 참조되지 않았고 git 변경을 통합하기 전에 생성 오류가 발견된 경우에는 올바른 ID로 수정할 수 있다.

새로운 판단과 확정이 필요하면 기존 ID를 변경하거나 재사용하지 않고 새로운 결정 ID를 부여한다.

### 5.7 결정 ID의 생성과 중복 확인

새로운 결정 파일을 생성하기 전에 해당 프로젝트에서 이미 사용 중인 결정 ID를 확인한다.

파일 생성 후 다음 사항을 확인한다.

- 기존 결정과 ID가 중복되지 않는가
- 파일 이름과 파일 내부의 결정 ID가 일치하는가
- 올바른 프로젝트 ID를 사용했는가
- 확정된 결정 ID 형식을 따르는가
- 이미 사용한 ID를 재사용하지 않았는가

사람이나 여러 AI Agent가 동시에 결정 파일을 생성할 수 있으므로 git 변경을 통합하기 전에 중복 여부를 다시 확인한다.

현재 중복과 파일 이름의 일치 여부는 수동으로 확인한다. 자동 생성 및 검증 방법은 필요할 때 별도 규칙으로 정의한다.

### 5.8 검토 중인 항목

- 결정 ID의 구성 요소와 최종 표기 형식
- 프로젝트 ID의 생성 및 발급 방법
- 동시 생성 충돌과 자동 생성·검증 방법

## 6. 결정 파일의 구조와 작성 형식

결정 기록은 하나의 Markdown 파일로 작성한다. 파일 상단에는 YAML 메타데이터를, 그 아래에는 Markdown 본문을 작성한다.

YAML 메타데이터를 별도의 YAML 파일로 분리하지 않는다.

사용:

```text
JPS001-D001.md
```

별도로 생성하지 않음:

```text
JPS001-D001.yaml
JPS001-D001-body.md
```

기본 구조는 다음과 같다.

```markdown
---
YAML 메타데이터
---

# 결정 제목

Markdown 본문
```

### 6.1 YAML 메타데이터의 역할

YAML 메타데이터에는 결정의 식별, 상태, 시점, 책임 및 연결 정보를 구조화하여 기록한다.

결정의 상세한 내용, 검토한 대안, 판단 이유 및 영향은 Markdown 본문에 기록한다.

### 6.2 YAML 예시 구조

다음 예시는 현재까지 확정된 필드와 검토 중인 필드를 함께 반영한 `decided` 상태의 예시이다. 이 예시는 최종 스키마가 아니며 검토 중인 필드는 변경되거나 제외될 수 있다.

```yaml
---
project_id: JPS001
project_name: "Java-POSSERVER"
id: JPS001-D001
title: "결정 기록 파일의 구조와 관리 규칙"

status: decided
risk_level: medium

created_at: 2026-10-21
decided_at: 2026-10-21

proposed_by: collaborative
adoption: modified
decided_by: "Sun&Moon"
decision_owner: PL

replaces: []

jira_issues:
  - PROJ-101
---
```

다른 상태에서는 일부 필드의 값이 존재하지 않을 수 있다. 상태별 필수 값과 빈 값 처리 방법은 7장에서 정의한다.

`replaces`는 모든 결정 파일에 포함하는 기본 필드로 사용한다.

YAML의 빈 줄은 필드 그룹을 구분하기 위한 것이며 별도의 데이터를 의미하지 않는다.

### 6.3 YAML 필드 그룹

#### 6.3.1 프로젝트와 결정의 식별

```yaml
project_id:
project_name:
id:
title:
```

- `project_id`: 프로젝트를 식별하는 고정값
- `project_name`: 사람이 읽는 프로젝트 표시 이름
- `id`: 개별 결정을 식별하는 고유 ID
- `title`: 사람이 읽는 결정 제목

결정 ID와 파일 이름의 규칙은 5장에서 정의한다.

#### 6.3.2 결정 상태와 위험 등급

```yaml
status:
risk_level:
```

- `status`: 결정 기록이 검토와 확정 과정에서 도달한 현재 상태
- `risk_level`: 결정안이 채택되어 적용됐을 때 발생할 수 있는 위험 수준

상태값, 상태 전환 및 위험 등급은 7장에서 정의한다.

#### 6.3.3 기록 및 결정 시점

```yaml
created_at:
decided_at:
```

- `created_at`: 결정 파일을 처음 생성한 날짜
- `decided_at`: 결정안을 공식 결정으로 채택한 날짜

날짜는 `YYYY-MM-DD` 형식으로 작성한다.

#### 6.3.4 제안 형성 방식과 채택 방식

```yaml
proposed_by:
adoption:
```

- `proposed_by`: 결정안이 사람, AI Agent 또는 협업을 통해 형성된 방식
- `adoption`: 제안된 결정안이 공식 결정에 반영된 방식

두 필드의 최종 이름, 허용값 및 사용 여부는 7장에서 정의하고 검토한다.

#### 6.3.5 결정자와 결정 책임

```yaml
decided_by:
decision_owner:
```

- `decided_by`: 결론을 공식 결정으로 확정한 사람
- `decision_owner`: 결정 절차와 기록 관리에 책임을 지는 역할

상태별 사용 조건과 권한은 7장에서 정의한다.

#### 6.3.6 결정의 대체 관계

모든 결정 파일에는 `replaces`를 목록 형태로 기록한다.

```yaml
replaces: []
```

하나 이상의 기존 결정을 대체하려는 경우 결정 ID를 기록한다.

```yaml
replaces:
  - JPS001-D005
  - JPS001-D008
```

적용 조건, 상태 연계 및 역방향 관계는 8장에서 정의한다.

#### 6.3.7 이슈 연결

현재 검토 중인 이슈 연결 필드는 다음과 같다.

```yaml
jira_issues:
  - PROJ-101
```

관련 이슈가 없으면 빈 목록을 사용한다.

```yaml
jira_issues: []
```

이슈의 제목, 담당자, 진행 상태, 일정 및 완료 여부는 결정 파일에 반복하여 기록하지 않는다.

### 6.4 Markdown 본문의 역할

Markdown 본문에는 결정안의 내용, 검토 과정, 판단 결과 및 해당 기록을 이해하는 데 필요한 설명을 기록한다.

다른 영역에서 관리되는 문제, 가정, 근거 및 관련 자료는 그대로 복제하지 않고 필요한 내용을 요약하거나 관련 기록을 참조한다.

### 6.5 Markdown 본문의 기본 구성

```markdown
# 결정 제목

## 결론

## 배경

## 검토한 대안

## 결정 이유

## 영향

## 미해결 질문

## 관련 기록
```

#### 결론

상태에 따라 제안된 결론, 확정된 결론 또는 검토 결과를 기록한다. 상태별 작성 규칙은 7장에서 정의한다.

#### 배경

결정이 필요해진 상황과 맥락을 기록한다. 다른 영역에서 관리되는 경우에는 필요한 내용만 요약하고 참조한다.

#### 검토한 대안

실제로 검토한 선택지를 기록한다. 검토하지 않은 대안을 사후에 검토한 것처럼 추가하지 않는다.

#### 결정 이유

결론을 선택하거나 결정안을 채택하지 않은 이유와 중요한 절충 내용을 기록한다.

#### 영향

영향을 받는 대상과 범위를 기록한다. 구체적인 실행 작업과 진행 상태는 이슈 관리에서 관리한다.

#### 미해결 질문

현재 기록에서 해결되지 않은 질문을 기록한다. 독립적인 판단과 확정이 필요하면 별도의 결정 후보나 관련 기록으로 분리한다.

#### 관련 기록

문제, 가정, 근거, 다른 결정, 이슈 및 관련 문서의 식별자나 참조 위치를 기록한다. 연결 방법은 8장에서 정의한다.

### 6.6 결정 제목의 일치

YAML의 `title`과 Markdown의 첫 번째 제목은 모두 사용하며 반드시 동일해야 한다.

```yaml
title: "결정 기록 파일의 구조와 관리 규칙"
```

```markdown
# 결정 기록 파일의 구조와 관리 규칙
```

제목을 변경할 때 두 값을 함께 수정한다.

### 6.7 필드와 값의 구분

```text
필수 필드
→ 결정 파일에 항상 존재하는 필드

필수 값
→ 특정 상태에서 반드시 기록해야 하는 값
```

목록 형태의 필드는 값이 없더라도 빈 목록을 유지한다.

```yaml
replaces: []
```

상태별 필수 값과 빈 값 처리 방법은 7장에서 정의한다.

### 6.8 작성 언어와 표기 원칙

YAML 필드 이름과 구조화된 값은 영어로 작성하고, 필드 이름에는 `snake_case`를 사용한다.

```yaml
status: decided
risk_level: medium
decision_owner: PL
```

프로젝트 이름, 결정 제목 및 Markdown 본문은 프로젝트의 기본 작성 언어를 사용한다.

동일한 의미의 필드 이름이나 구조화된 값을 여러 언어 또는 표기 방식으로 혼용하지 않는다.

### 6.9 검토 중인 항목

- `project_name`을 파일마다 기록할지 프로젝트 공통 설정으로 이전할지 여부
- 값이 없는 단일 필드를 생략할지 `null`로 유지할지 여부
- 날짜 값을 따옴표로 감싼 문자열로 기록할지 여부
- `jira_issues`를 유지할지 `issues`로 일반화할지 여부
- Markdown 본문의 필수 구역과 선택 구역
- 내용이 없는 선택 구역의 처리 방법
- 근거 요약과 참고자료 구역의 필요성
- YAML과 Markdown의 자동 생성 및 검증 방법

## 7. 결정의 상태, 위험 등급 및 책임

이 장에서는 상태, 상태 전환, 상태별 필수 정보, 위험 등급, 제안과 채택 방식, 결정자, 결정 책임 및 사람과 AI Agent의 권한을 정의한다.

### 7.1 결정 상태의 역할

`status`는 결정의 구체적인 내용이 아니라 결정안이 검토와 확정 과정에서 도달한 상태를 나타낸다.

```text
결정의 내용
→ 사람이 무엇을 하거나 하지 않기로 판단했는가

결정의 상태
→ 결정안이 검토와 확정 과정에서 어느 단계에 있는가
```

`go`, `pivot`, `hold`, `stop`과 같은 실행 방향은 상태가 아니라 결론에 기록한다.

### 7.2 결정 상태값

```text
proposed
decided
deferred
rejected
superseded
```

#### `proposed`

결정안이 작성되었지만 아직 공식 결정으로 채택하거나 거부하지 않은 상태이다. 확정된 결정이나 현재 규칙으로 사용하지 않는다.

#### `decided`

결정안이 사람에 의해 채택되어 공식 결정으로 확정된 상태이다.

공식 결론은 새로운 방식의 채택, 기존 방식의 유지 또는 특정 방식의 중단 등으로 나타날 수 있다.

`decided`는 공식 결정의 확정을 의미하며, 현재 규칙 반영과 실행 작업 생성은 8장에서 정의한다.

#### `deferred`

결정안의 검토와 확정을 이후로 미룬 상태이다. 공식적으로 채택되거나 거부된 결론이 존재하지 않는다.

#### `rejected`

결정안을 검토했지만 공식 결정으로 채택하지 않기로 확정한 상태이다. 거부된 결정안도 삭제하지 않고 검토 이력으로 보존한다.

#### `superseded`

기존 결정이 새로운 결정으로 대체되어 더 이상 현재 유효한 결정으로 사용되지 않는 상태이다. 대체된 결정 파일은 삭제하거나 새 결론으로 덮어쓰지 않는다.

### 7.3 상태 전환

```text
proposed → decided
proposed → deferred
proposed → rejected

deferred → proposed

decided → superseded
```

보류된 결정안을 채택하거나 거부하려면 먼저 `proposed`로 변경하여 검토를 재개한다.

```text
deferred → proposed → decided
deferred → proposed → rejected
```

다음 전환은 허용하지 않는다.

```text
rejected → proposed
rejected → decided
superseded → proposed
superseded → decided
```

거부되거나 대체된 내용을 다시 검토하려면 새로운 결정 ID를 부여한다.

표현 보완과 오탈자 수정은 기존 파일에서 할 수 있지만, 기존 결론과 다른 판단은 새로운 결정 파일로 기록한다.

상태 변경 이력은 git에서 보존한다.

### 7.4 상태별 필수 정보

모든 상태에서 다음 정보를 유지한다.

- 결정 ID와 제목
- 생성일
- 제안 형성 방식
- 위험 등급 또는 위험 등급 후보
- 결정 책임 역할
- `replaces`

#### `proposed`

- 검토할 결정안이 있어야 한다.
- `decided_at`, `decided_by`, `adoption`은 아직 값이 없다.
- `replaces`는 대체 후보이며 기존 결정의 상태를 변경하지 않는다.

#### `decided`

- `decided_at`, `decided_by`가 필요하다.
- `adoption`을 사용하기로 확정하면 값이 필요하다.
- 공식 결론, 결정 이유 및 영향이 필요하다.
- 위험 등급은 사람이 확인한 값이다.

#### `deferred`

- 보류 이유와 재검토 시점 또는 조건이 필요하다.
- `decided_at`, `decided_by`, `adoption`은 값이 없다.
- `replaces`는 기존 결정에 영향을 주지 않는다.

#### `rejected`

- 거부 이유, 거부 확정자 및 확정일이 필요하다.
- `adoption`은 사용하지 않는다.
- `replaces`는 확정된 대체 관계로 적용하지 않는다.

#### `superseded`

- 기존의 확정 정보, 결론 및 판단 이유를 그대로 유지한다.
- 대체 시점과 대체 결정의 연결 방법은 8장에서 정의한다.

### 7.5 위험 등급

`risk_level`은 결정안이 채택되어 적용됐을 때 잘못되거나 예상과 다르게 작동하는 경우 발생할 수 있는 영향의 범위, 심각도 및 복구 난이도를 나타낸다.

```text
low
medium
high
```

- `low`: 영향 범위가 제한적이고 복구가 쉬우며 일반적인 검토로 관리할 수 있다.
- `medium`: 여러 구성요소에 영향을 줄 수 있고 복구에 비용과 조정이 필요하며 별도 검토가 필요하다.
- `high`: 시스템 구조, 보안, 데이터 또는 운영 안정성에 큰 영향을 줄 수 있고 복구가 어렵거나 비용이 크며 강화된 승인과 검증이 필요하다.

여러 조건에 해당하면 더 높은 등급을 우선한다.

`proposed`와 `deferred`의 위험 등급은 후보값이며, `decided`와 `rejected`에서는 사람이 확인한 값이다.

AI Agent는 후보를 제안할 수 있지만 최종 위험 등급과 위험 수용 여부는 사람이 확인한다.

### 7.6 제안 형성 방식

현재 `proposed_by`는 결정안이 형성된 방식을 나타내기 위한 필드이다.

```text
human
ai_agent
collaborative
```

파일 작성자와 변경 이력은 git에서 관리한다. 필드명이 실제 의미에 맞는지는 추가 검토한다.

### 7.7 채택 방식 후보

`adoption`은 현재 검토 중인 선택 필드로, 제안된 결정안이 공식 결정에 반영된 방식을 나타내기 위한 후보이다.

```text
as_proposed
modified
```

- `as_proposed`: 제안된 결론을 주요 변경 없이 채택
- `modified`: 사람이 검토하고 수정하여 채택

`adoption`은 `decided` 상태에서만 사용하고, `superseded` 상태에서는 기존 값을 유지한다.

### 7.8 결정자와 결정 책임

`decided_by`는 결론을 공식 결정으로 확정한 사람을 기록한다. AI Agent는 이 값이 될 수 없다.

`decision_owner`는 다음을 관리하는 책임 역할이다.

- 필요한 검토 수행 여부
- 결정 범위와 위험 등급
- 적절한 권한자의 확정 여부
- 결정 기록 형식
- 상태와 기록의 일관성

`decision_owner`는 실행 작업의 담당자를 의미하지 않는다.

### 7.9 사람과 AI Agent의 권한

AI Agent는 다음 작업을 수행할 수 있다.

- 문제와 결정 후보 식별
- 대안 제안과 비교
- 자료 조사와 정리
- 결정 기록 초안 작성
- 위험 등급 후보 및 상태 변경안 제안
- 누락, 모순 및 형식 오류 검사
- 사람의 승인에 따른 파일 수정

AI Agent는 사람의 승인 없이 다음을 수행할 수 없다.

- 상태를 `decided` 또는 `rejected`로 확정
- 위험을 수용
- 자신을 결정자나 거부 확정자로 기록
- 확정된 결론을 다른 결론으로 변경
- 기존 결정을 공식적으로 대체

파일을 AI Agent가 수정하더라도 결정자와 거부 확정자는 이를 승인한 사람으로 기록한다.

사람은 방향과 범위 판단, 위험 수용, 채택·거부·보류, 대체 승인 및 상태 변경의 최종 책임을 가진다.

### 7.10 검토 중인 항목

- `decided`와 `rejected`의 공통 확정자 및 확정일 필드
- 중복 생성, 작성 오류 및 제안 철회 처리
- 거부된 결정안의 재검토 연결 방식
- 위험 등급의 상세 판정 및 승인 기준
- 위험 등급의 상향·하향 권한
- `proposed_by`를 `proposal_source`로 변경할지 여부
- `adoption` 필드의 유지 여부와 비교 기준
- 공동 확정자의 표기 방법
- `decision_owner`의 기본값, 허용 역할 및 상속 방식

## 8. 결정의 연결과 현재 상태 반영

결정 기록은 다른 결정, 관련 기록, 이슈, git 변경 이력 및 현재 규칙과 연결될 수 있다.

이 장에서는 각 정보의 책임 위치와 연결 및 반영 규칙을 정의한다.

### 8.1 연결의 기본 원칙

- 동일한 정보를 여러 위치에서 원본으로 관리하지 않는다.
- 각 정보는 해당 정보를 책임지는 위치에서 관리한다.
- 결정 파일에는 식별자나 참조 위치만 기록하고 전체 내용을 반복하지 않는다.
- 확정되지 않은 관계는 현재 유효한 관계로 적용하지 않는다.
- 자동 생성된 목록이나 Graph는 독립된 원본으로 사용하지 않는다.

```text
결론, 배경 및 이유
→ 결정 파일

현재 적용 기준
→ 규칙 문서

작업, 담당자 및 진행 상태
→ 이슈 관리 시스템

변경 이력
→ git

관계 정보
→ 관계를 선언한 개별 기록
```

### 8.2 관련 기록과의 연결

결정은 문제, 가정, 근거, 기회, 비전, 다른 결정, 현재 규칙, 실행 이슈 및 관련 문서와 연결될 수 있다.

가능한 경우 안정적인 식별자나 저장소 내부 참조 위치를 사용한다.

```markdown
## 관련 기록

- 문제: `JPS001-P003`
- 근거: `JPS001-E005`
- 관련 결정: `JPS001-D004`
- 이슈: `PROJ-101`
```

관련 기록은 결정이 다루는 문제와 근거, 같은 주제의 과거 검토, 실행 이슈 및 현재 규칙을 확인하기 위해 연결한다.

YAML에 구조화할지 Markdown에 기록할지는 추가 검토한다.

### 8.3 결정 간 관계와 대체

현재 구조화된 결정 관계는 `replaces`이다.

`replaces`는 일반적인 관련 결정 목록이 아니다.

```text
두 결정을 함께 적용할 수 있음
→ 대체 관계가 아님

새로운 결정이 기존 결론을 대신함
→ 대체 관계
```

대체 관계는 새로운 결정이 `decided` 상태일 때만 발효된다.

```yaml
# 새로운 결정
id: JPS001-D012
status: decided
replaces:
  - JPS001-D005
```

```yaml
# 기존 결정
id: JPS001-D005
status: superseded
```

두 변경은 하나의 git 변경 단위에서 함께 처리한다.

기존 결정에는 `superseded_by`를 기록하지 않는다. 역방향 관계는 `replaces`를 기준으로 계산한다.

거부된 결정안이나 같은 주제의 과거 검토는 `replaces`가 아니라 관련 기록으로 연결한다.

### 8.4 대체 관계의 검증

- `replaces`의 ID가 존재하는가
- 자기 자신을 대체하지 않는가
- 동일 ID가 중복되지 않았는가
- 새로운 결정이 `decided` 상태인가
- 대체 대상이 기존 공식 결정인가
- 기존 결정이 `superseded`로 변경되었는가
- 단순한 참고·확장·보완을 대체로 잘못 표현하지 않았는가
- 두 결정을 함께 적용할 수 없는가

하나의 결정은 여러 기존 결정을 대체할 수 있다. 부분 대체의 처리 방법은 추가 검토한다.

### 8.5 이슈 및 실행 작업과의 연결

```text
결정 기록
→ 무엇을 왜 결정했는가

이슈 관리
→ 어떤 작업을 누가 언제 수행하는가
```

결정 파일에는 대표 이슈의 ID만 기록하고 제목, 담당자, 상태, 일정, 우선순위 및 완료 여부는 이슈 관리 시스템에서 관리한다.

하나의 결정은 여러 이슈와 연결될 수 있고, 하나의 이슈도 여러 결정과 관련될 수 있다.

결정이 `decided`여도 실행 작업이 필요하지 않을 수 있다. 실행 작업이 필요하면 이슈를 생성하고 결정 ID를 참조한다.

결정이 변경되거나 대체되면 관련 이슈에 미치는 영향을 확인한다.

### 8.6 Git 변경 이력과의 연결

Git은 결정 파일과 관련 문서 및 소스의 변경 이력을 관리한다.

파일 작성자, 변경 시점, 변경 전후 내용 및 관련 커밋은 YAML에 반복하여 기록하지 않는다.

필요하면 커밋이나 코드 변경 요청에 결정 ID를 포함한다.

```text
git에 결정 파일이 존재하거나 병합됨
≠ 공식 결정으로 확정됨

소스가 구현됨
≠ 결정이 현재 규칙에 반영됨
```

공식 결정 여부는 결정 파일의 상태와 사람의 확정 기록을 기준으로 판단한다.

### 8.7 결정 기록과 현재 규칙의 구분

```text
결정 기록
→ 특정 결론의 배경, 대안 및 이유를 보존하는 이력

현재 규칙
→ 지금 따라야 하는 기준과 행동을 설명하는 원본
```

`decided` 상태가 되었다고 결정 파일이 항상 현재 규칙을 대신하는 것은 아니다. 지속 적용 기준이라면 규칙 문서에 반영한다.

새 결정이 기존 결정을 대체하면 다음을 확인한다.

- `replaces`가 올바른가
- 기존 결정이 `superseded`인가
- 현재 규칙이 새 결정과 일치하는가
- 더 이상 유효하지 않은 규칙이 수정되었는가
- 필요한 이슈가 생성되거나 갱신되었는가

### 8.8 Graph의 역할

Graph는 결정과 관련 기록 사이의 관계를 조회하고 탐색하기 위한 파생 결과이다.

Graph는 개별 기록과 관계의 원본을 대신하지 않는다.

역방향 대체 관계는 `replaces`를 기준으로 계산한다.

Graph의 생성, 저장, 갱신 및 검증 방식은 추가 검토 후 정의한다.

### 8.9 연결 정보의 검증

- 참조 대상이 존재하는가
- 같은 관계를 여러 위치에서 다르게 기록하지 않았는가
- 결정과 현재 규칙이 충돌하지 않는가
- 결정 변경이 관련 실행 작업에 반영되었는가
- 파생 목록이나 Graph가 원본과 일치하는가

대체 관계 전용 검증은 8.4를 따른다.

AI Agent는 누락과 불일치를 검사하고 수정안을 제안할 수 있으며, 최종 변경은 사람이 승인한다.

### 8.10 검토 중인 항목

- `replaces` 이외의 구조화된 관계 필드
- 일반 관련 기록의 YAML 또는 Markdown 기록 위치
- 거부된 결정안과 새 결정의 연결 방식
- 기반·보완·부분 대체 관계의 처리
- 관계 순환 허용 여부
- 관련 기록의 ID와 이동·삭제 처리
- `jira_issues`를 `issues`로 일반화할지 여부
- 이슈와 git에서 결정 ID를 표기하는 방법
- 현재 규칙의 저장 위치와 반영 완료 관리
- Graph의 생성, 저장, 갱신 및 검증 방식

## 9. 검토 항목과 기준 버전 관리

확정된 규칙은 해당 주제를 다루는 장의 본문에서 관리한다.

검토 중인 사항은 해당 장의 `검토 중인 항목`에서 관리하며 공식 규칙이나 AI Agent의 실행 기준으로 사용하지 않는다.

조사, 비교, 문서 수정 및 자동화 작업은 이슈 관리 시스템에서 관리한다.

### 9.1 검토 항목의 관리 원칙

- 동일한 검토 항목을 여러 장에 중복하여 기록하지 않는다.
- 다른 장과 관련된 사항은 내용을 복사하지 않고 해당 장을 참조한다.
- 별도의 판단이 필요한 사항은 결정 후보로 분리한다.
- AI Agent는 선택지를 조사하고 수정안을 작성할 수 있지만 사람의 확인 없이 규칙을 확정할 수 없다.
- 자동화 방법만 미확정인 경우에는 현재 정의된 수동 절차를 따른다.

### 9.2 검토 항목의 확정과 반영

```text
선택지와 영향 분석
→ 위험 등급 확인
→ 사람의 명시적인 결정
→ 관련 장의 본문과 예시 수정
→ 연관된 장의 일관성 확인
→ 검토 항목에서 제거
→ git 변경 이력으로 보존
```

확정된 규칙의 원본은 해당 주제를 다루는 장의 본문이다.

관련 장의 설명과 예시가 일치하지 않으면 변경이 완료된 것으로 처리하지 않는다.

### 9.3 기준 버전 확정

이 명세는 다음 조건을 충족하면 기준 버전으로 확정할 수 있다.

- 본문의 규칙 사이에 모순이 없다.
- 본문의 규칙과 예시가 일치한다.
- 결정 파일을 생성하고 검토하는 기본 절차가 정의되어 있다.
- 사람과 AI Agent의 권한이 구분되어 있다.
- 결정 기록, 현재 규칙, 이슈 관리 및 git의 역할이 구분되어 있다.
- 미확정 사항이 확정된 규칙과 명확하게 구분되어 있다.
- 남은 미확정 사항이 기본 운영을 방해하지 않는다.

모든 자동화 방법이 확정되어야만 기준 버전을 만들 수 있는 것은 아니다.

ID 자동 발급, 구조 검증, 이슈 연동, Graph 생성 및 관계 검사는 기준 버전 확정 이후에도 추가할 수 있다.

기준 버전 확정 후 규칙을 변경해야 한다면 기존 규칙을 임의로 덮어쓰지 않고 새로운 결정으로 변경 근거를 남긴다.
