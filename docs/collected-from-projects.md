# 프로젝트에서 모은 것

Rules를 실제 프로젝트(KEDP001, SOPS001)에 적용하면서 나온 개선 후보를 모은다.

- 나온 그대로 적는다. 정리와 분석은 프로젝트가 완료된 뒤 하나로 묶을 때 한다(DEC-025).
- 항목마다 출처와 날짜를 붙인다.
- 공개 저장소이므로 서버 이름, 보안 설정 값 같은 업무 대외비는 일반적인 말로 바꿔 적는다.
- 새로 나온 것은 이 문서에 바로 추가한다.

## 2. 모아 둔 것: SOPS001

출처: SOPS001 세션이 정리한 목록 (2026-10-25, 대화로 받음)

### A. 개발 진행 단계

- 있었던 일: "프로그램을 만들어 주세요" 앞에서 무엇을 먼저 정해야 하는지가 Rules에 없어서 매번 순서를 새로 짰다.
- 넣을 것: 개발을 단계로 나누고, 단계마다 시작 전에 정해야 할 것을 적는다.

  ```text
  결정(범위·구조·설정·보안) → API 약속 → 화면(dummy) → Backend → 가짜 서버 시험 → 실제 환경 → 배포
  ```

  예: "화면을 만들기 전에 API 약속이 정해져 있어야 한다". 이것이 있으면 AI도 "아직 API 약속이 없으니 먼저 정하자"고 말할 수 있다.
- 착수 조건 자체는 v0.5.0에 반영했다. 단계의 순서는 SOPS에만 있다.

### B. 결정 기록(07) 보완

1. **대화 합의를 결정으로 옮기는 절차**: 많은 대화 합의(약 60개)를 정리 문서 → 묶음안 → 5개씩 `proposed` → `decided`로 옮겼다. 이 절차와 정리 문서 양식이 Rules에 있으면 다음 프로젝트는 바로 따라 할 수 있다.
2. **관련 기록에는 이미 있는 ID만**: 아직 없는 결정 번호를 미리 적었다가 고쳤다. "앞으로 만들 결정은 번호 대신 말로 적는다"를 규칙으로 넣으면 막을 수 있다.
3. **결정 칸을 사람이 바꿀 때의 실수 방지**: 옛 줄이 남아 칸이 두 번 생기거나, 파일 몇 개를 빠뜨렸다. 00.common §12.1의 "검증 Script"를 실제로 만들 차례다(칸 중복, 빠진 칸, 없는 ID 참조 검사).
4. **위험 수용을 적는 곳**: 평문 통신이나 넓은 파일 권한처럼 "알고 감수한다"를 지금은 본문 "영향"에 한 줄로 적었다. 정해진 자리가 있으면 나중에 찾기 쉽다.

### C. 비어 있는 영역 채우기

1. **설계 문서의 위치와 역할**: 설계 문서 여러 개와 화면 설계서를 둘 곳이 없었고, 그래서 결정의 근거로 가리키지도 못했다. (`docs/`는 v0.5.0에 반영. `current-state.md`와의 역할 구분은 남음)
2. **08.execution**: 결정 → GitHub Issue → branch → PR → squash merge 흐름, branch 이름 규칙, PR과 Issue가 번호를 함께 쓴다는 점, `Closes #번호`
3. **03.assumptions**: 확인 목록처럼 "아직 확인하지 않은 전제"를 적고, 확인되면 닫는 곳
4. **04.evidence**: "Sun&Moon 확인(날짜)"처럼 사람이 확인한 사실을 근거로 남기는 형식

### D. AI와 함께 일하는 방식

1. **협업 원칙을 `CLAUDE.md` 템플릿에**: 실행 전에 확인받기와 git은 v0.5.0에 반영했다. "저장소 문서에 업무 대외비를 쓰지 않는다"는 SOPS에만 있다.
2. **AI 세션 사이의 기억 넘기기**: Windows와 Linux의 Claude는 기억을 공유하지 않아서 정리 문서를 만들어 넘겼다. 원칙은 v0.5.0에 반영했다. 정리 문서의 양식은 남음.
3. **독립 AI 검토를 실제로 하는 방법**: Rules에는 "해야 한다"만 있고 "어떻게"가 없다. 예: "새 세션에서 `gh pr diff`로 보고 검토, 결과는 PR 댓글로"

### E. 템플릿과 도구

1. **PR 템플릿**: 체크리스트를 "결정 기록이 있을 때만"으로 묶기, 검토 결과에 "해당 없음" 넣기
2. **실제 설정과 비밀은 저장소 밖**: 원칙은 v0.5.0에 반영했다. `.gitignore`와 예시 설정 파일(`config-samples/`) 템플릿은 남음.

### 참고

- 이슈 번호는 `schware/aidev-SOPS001#12` 모양으로 적는다(DEC-024). SOPS001이 v0.5.0으로 옮겨 갈 때 `project.yaml`의 `issue_patterns`도 이 모양으로 맞춘다.

## 3. 모아 둔 것: KEDP001

원본: [kedp-lessons-for-ai-native-development.md](kedp-lessons-for-ai-native-development.md) (Sun&Moon 작성, 2026-10-25)

원본 문서의 "다음 버전에 넣을 우선순위" 가운데 v0.5.0에 반영하지 않은 것:

- 실행 작업의 세 칸: 할 일, 끝났다는 기준, 하지 말 것 (+ Issue 양식 파일 `.github/ISSUE_TEMPLATE/`)
- 문서 종류와 위치의 표준: 결정, 명세, 규칙(`.claude/`), 작업(Issue), 안내서(`docs/`), 근거(`samples/`)
- D로 남기는 기준과 Agent가 스스로 정해도 되는 범위
- 용어 정의 칸: 같은 말이 두 가지로 읽히면 이름을 나눈다
- 반복 구조의 원칙: 확실한 공통은 먼저, 나머지는 붙여 보며, 고칠 때마다 테스트. "근거 확보"와 "기능 완성"을 다른 단계로
- 기록이 merge된 것을 확인한 뒤 작업을 요청한다
- 위임 수준의 단계(안내만 → 작업까지 → PR까지 → merge까지)와 사람에게 묻는 방식
- 도구를 들이는 기준과 MVP 범위를 줄이는 기준
- "같은 문제가 두 번 나면 기록한다"를 안내서의 "막히면" 표로 운영

대화로 받은 KEDP 목록(12개)에만 있고 원본 문서에는 없는 것:

- **규칙에 출처 결정 ID 붙이기**: 예: "키 값을 출력하지 않는다 (D012)". 결정이 바뀌면 고칠 규칙을 바로 찾을 수 있다.
- **Agent 규칙 파일을 짓는 원칙**: 넣는 것(어기면 사고가 나는 행동 규칙)과 빼는 것(찾아보면 되는 정보, 중복, 도구가 막아 주는 것)의 기준
- **프로젝트 시작 체크리스트**: 저장소 생성, 비공개 설정, 키 보호, commit 이메일, hook 연결, 개발 서버 설치. 반복되는 것은 템플릿으로
- **사람이 할 일 칸**: 사이트 가입, 키 발급, 승인, merge처럼 사람만 할 수 있는 일을 단계마다 따로 적는다
- **Issue 칸**: 목록에서는 7칸(할 일, 역할, 담당 폴더, 근거 결정 ID, 완료 기준, 확인 방법, 하지 말 것)이었으나, 원본 문서에서는 3칸으로 줄었다

## 4. Sun&Moon이 짚은 것

출처: Rules 저장소 세션 대화 (2026-10-24 ~ 2026-10-25)

1. **파일 이름 규칙** (Sun&Moon: "가장 중요")
   - AI마다 파일과 폴더 이름을 만드는 규칙이 다르다. 지금 Rules에는 기록 파일 이름을 기록 ID와 같게 한다는 규칙(00.common §7.5)만 있다.
   - 번호 매기기도 세션마다 다르다(1/2/3, A/B/C). 프로젝트 이름도 대문자와 소문자가 섞인다. 적힌 규칙이 없으면 대화에 먼저 나온 모양이 그 세션의 규칙이 된다.
2. **사람이 정리해서 올려 놓는 공간**
   - AI에게 일을 시키려고 만든 파일(요청서, 세션 사이에 넘기는 정리 문서, 자료)을 둘 곳이 없다. AI가 매번 지킬 규칙(`CLAUDE.md`, `.claude/`)과는 다르다.
   - 분석을 요청할 때 대화에 붙여 넣는 방식이 아니라, 저장소에 올려 놓고 요청하는 문서 기반이 필수가 된다. 지금 두 프로젝트에는 적용하지 않고, 이후 버전에서 해 본다.
3. **사람이 코딩할 영역을 정하는 방법**
   - 큰 틀은 AI로 만들 때 사람이 맡을 곳을 어떻게 정하는가. 제안: 폴더마다 세 단계 중 하나로 정한다 — 사람이 쓴다 / 사람이 읽고 승인한다 / AI에 맡기고 테스트로 확인한다.
   - 00.common §5.4에는 "어떻게 함께 일하나"는 있지만 "어느 영역에서"는 없다. KEDP의 proto 폴더(Agent는 변경안만, 사람이 승인)가 이미 두 번째 단계의 예다.
4. **신뢰** (README "방향성" 후보)
   - "결국 서로 믿고 작업한다가 시작이다. 그래서 Rules를 더 명확하게 정리하고 적어야 서로 신뢰가 생긴다. 좋으면서 어렵고, 인간관계보다 명확하다." — Sun&Moon
   - 신뢰는 "그냥 믿기"가 아니라 "확인할 수 있어서 믿기"다. 확인이 쌓이면 맡기는 범위를 넓힌다.
5. **일을 시키는 방식**
   - 무엇을 할지는 Issue(명령은 "#14를 읽고 진행" 한 줄), 긴 내용은 저장소 파일(Issue가 가리킴), 매번 같은 방식은 Claude Code 명령 파일.
   - 예: `/work 14` → Issue 읽기 → 착수 조건 확인 → 세 칸 확인받기 → 작업. starter 템플릿 후보.
6. **개발 완료 문서**
   - 언어(구성 요소)별 개발이 마무리되면, 무엇을 어떻게 만들었고 어떻게 진행했는지 정리하는 문서를 만든다.
   - Claude Code가 문서를 잘 만들게 하려면 일을 시킬 때와 같이 요청한다: 독자와 목적, 양식(목차), 읽을 재료, 저장 위치, 하지 말 것(기록에 없는 것을 지어내지 않기), 끝났다는 기준(문장마다 출처), 목차를 먼저 확인받기.
   - Sun&Moon이 짚은 빠진 점: "가장 중요한 어디에 적어야 할지가 없다". 문서 요청에는 저장 위치와 파일 이름이 꼭 들어가야 한다.
   - 양식 초안 (starter 템플릿 후보):

     ```markdown
     # <구성 요소> 개발 완료 문서

     - 대상 폴더: <예: src/backend/>
     - 저장 위치: docs/dev-complete/<대상 폴더 이름>.md
     - 독자: 새로 온 개발자. 이 문서만 보고 실행하고 구조를 이해할 수 있어야 한다.
     - 작성 규칙: 문장마다 출처(결정 ID, Issue 번호, 파일 경로)를 붙인다. 기록에 없는 것은 "확인 필요"로 적는다.

     ## 1. 한 줄 요약
     ## 2. 실행하는 방법
     ## 3. 구조 (폴더와 주요 파일)
     ## 4. 데이터 흐름
     ## 5. 주요 결정 (결정 ID와 한 줄 이유)
     ## 6. 진행 과정 (Issue와 PR 순서)
     ## 7. 부딪힌 문제와 해결
     ## 8. 확인 필요
     ```

7. **할 일 목록의 위치**
   - TODO 같은 할 일 파일을 README와 같은 루트에 두면 압박감이 크다. 둔다면 루트가 아닌 곳에 둔다. 할 일 목록 방식 자체는 고민 중.
