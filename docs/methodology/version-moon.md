# Version Moon

- 확정: 2026-11-14, Sun&Moon
- 공통 원칙과 공통 장치(작업 요청 형식, PR 보고, 결정 기록 쓰는 법, 다섯 줄 확인, 막는 장치)는 [`README.md`](README.md)에 있다.

## 한눈에
- 처음에 헌장 하나로 목표와 끝을 정한다.
- 그 뒤로는 Issue 하나씩 만들고 돌아보며 나아간다. 열린 Issue는 늘 하나다.
- 보조 장치는 처음부터 두지 않는다. Issue를 시작할 때의 점검과, 진행 중에 생긴 일로 켠다.

## 왜 이렇게 하는가
사람 팀에는 기억하고, 되묻고, 반대하고, 만드는 데 시간이 드는 자연스러운 안전장치가 있다. AI Agent에는 이것이 없다. 그래서 빈칸을 추측으로 채우고 "가능합니다", "완료했습니다"라고 말한다. Version Moon은 이 안전장치를 체크리스트로 다시 세운 Agile이다. 막힐 것을 미리 가정하지 않고, 일이 생겼을 때만 장치를 켠다.

## 흐름

```text
헌장 → [ Issue 시작 점검 → 진행 → Issue 마무리 → 회고 ] 반복 → 끝 (완료 또는 보관)
```

## 1. 헌장 (`docs/plan-baseline.md`)
프로젝트에 하나만 둔다. 모두 채워야 시작한다.
- [ ] **목표 (Goal)**: 누구를 위해, 무엇을 만들어, 어떤 문제를 푸는가
- [ ] **하지 않는 것 (Out of Scope)**
- [ ] **MVP**: 첫 번째 릴리스가 끝났을 때 쓸 수 있는 상태. 한두 문장
- [ ] **큰 그림 (Epic 목록)**: 릴리스 후보의 이름과 최소 목표 한 줄씩. Learning에서 그린 한 장을 결정한 것이다. 자세한 내용(Story, 일정)은 Learning 공간에 두고 저장소에는 두지 않는다
- [ ] **멈출 조건 (Stop Condition)**: 이것이 드러나면 멈춘다. 없으면 "없음"
- [ ] AI가 낸 더 작은 안, 더 큰 안, "실패한다면 이유는?"을 보고 사람이 정했다
- [ ] 결정 기록으로 남기고, AI가 고칠 수 없도록 잠갔다
- [ ] **첫 Issue**: 처음부터 끝까지 한 번 이어지는 가장 작은 기능

헌장은 고정한다. 목표나 하지 않는 것을 바꿔야 할 때만 결정 기록을 남기고 고친다. 큰 그림도 헌장과 함께 고정한다. 큰 그림은 결정된 방향이고, 바뀌는 것은 다음에 무엇부터 할지다. 방향이 바뀔 때만 결정 기록을 남기고 큰 그림을 고친다. 전혀 다른 제품을 만들고 싶으면 이 프로젝트를 끝내고 새 프로젝트를 시작한다.

## 2. Issue 시작 점검 (Definition of Ready)
**꼭 쓸 것**
- [ ] 끝났다는 기준
- [ ] 예상 기간

**사람이 답할 질문** (그렇다면 해당 장치를 켠다)
- [ ] 밖에서 기다려야 하는 것이 있는가 → **막힌 일**
- [ ] 모르거나 아직 정하지 않은 것이 있는가 → **스파이크, 결정 후보**
- [ ] 사람에게 보내거나, 밖으로 나가거나, 데이터를 지우거나 바꾸는가 → **가정 목록**
- [ ] 기다리는 Issue가 둘 이상인가 → **릴리스 계획, 백로그**

## 3. 진행 중 지켜볼 것 (AI가 센다)
하나라도 해당하면 AI는 알리고 멈춘다.
- [ ] 예상 기간의 두 배를 넘었다 → **위험**
- [ ] 같은 오류를 세 번 넘게 고치려 했다 → **위험**
- [ ] 헌장의 멈출 조건에 해당한다 → **위험**. 멈추고 사람이 결정한다
- [ ] 가정 목록에 없는 가정이 새로 필요하다 → **가정 목록에 더한다**
- [ ] 막힌 일이 3개가 되었다 → **진행을 멈춘다**
- [ ] 회고 생략이 3번 이어졌다 → **진행을 멈춘다**

## 4. Issue 마무리 (Definition of Done)
**PR 보고**: [`README.md`](README.md) 3.2를 따른다.

**회고 (`docs/journey.md`, 사람이 먼저 쓴다)**
- [ ] 잘 안 된 것. 없으면 "없음", 쓰지 못했으면 "생략". 둘은 다르다
- [ ] 알게 된 것

## 5. 새 session을 시작할 때
- session은 회고를 마친 뒤에만 바꾼다.
- 새 session은 [`README.md`](README.md) 3.4의 다섯 줄 확인을 한다. 셋째 줄에는 켜져 있는 장치(막힌 일, 위험, 백로그)를 적는다.

## 6. 끝
- [ ] **완료**: MVP에 닿았다. 더 갈지는 릴리스 계획에서 정한다
- [ ] **보관**: 더 진행하지 않는다. 배운 것을 마지막 회고에 남긴다

## 7. 필요할 때 켜는 장치
- AI는 켜야 할 때를 보면, **어떤 장치를 왜 켜야 하는지 말하고 멈춘다.** 켤지는 사람이 정한다.
- 할 일이 끝나면 끈다.

| 장치 | 하는 일 | 끄는 때 |
|---|---|---|
| **막힌 일** | Issue에 `blocked` 라벨을 붙이고, 무엇을, 누구를, 언제까지 기다리는지 적는다. 그동안 다른 Issue를 먼저 한다. **3개가 되면 Claude Code는 진행을 멈추고** 릴리스 계획을 연다 | 풀리면 라벨을 떼고 이어서 한다 |
| **스파이크** | 확인할 질문, 끝나는 기준, 기간을 정한 Issue 하나로 만든다. 따로 branch에서 하고 merge하지 않는다. 결과는 결정 기록으로 남긴다 | 기간이 지나거나 답이 나오면 닫는다 |
| **결정 후보** | AI가 결정 후보를 쓴다. 찾아본 기존 결정과 바꾸는 것을 함께 적는다. Issue에 `decision-needed` 라벨을 붙인다. 결정 전에는 그 부분을 시작하지 않는다 | 사람이 결정하면 끝난다 |
| **가정 목록** | AI가 5W2H 표를 만들고, 칸마다 "요청", "가정", "빈칸"으로 표시한다. 사람은 "가정"만 보고 "빈칸"은 반드시 채운다. 확인한 표에서 시나리오와 test를 만든다 | 표를 확인하면 끝난다. 새 가정이 생기면 다시 켠다 |
| **릴리스 계획** | 결정을 기다리는 것과 막힌 일부터 본다. 헌장의 큰 그림에서 다음 릴리스를 고르고, 고른 결과는 `docs/plan.md`에 적는다. 릴리스 목표와 끝났다는 기준을 정하고, 이번에 할 Issue를 고른다. "이번 릴리스가 실패한다면 이유는?"을 묻는다 | 릴리스가 끝나면 끝난다 |
| **백로그** (`docs/backlog.md`) | 릴리스 계획 때만 채운다. 이번 릴리스에서 할 Issue만, 최대 5개. 넘으면 릴리스를 나눈다. 릴리스 중에는 목표에 꼭 필요한 것만 더한다. 넣고 순서를 정하는 것은 사람이 한다 | 비면 끈다. 릴리스가 끝날 때 남은 것은 넘길지 버릴지 정한다 |
| **위험** (`docs/risks.md`) | 신호를 셀 수 있는 사실로 적고 대응을 정한다. 멈출 조건에 해당하면 멈추고, 계속, 목표 변경, 보관 중 하나를 결정 기록으로 남긴다 | 신호가 사라지거나 결정이 나면 "닫힘" |

## 10. 용어 대응
이 방법론에서의 대응이다. 일반 Agile에서 Epic은 여러 릴리스에 걸치기도 하지만, 여기서는 Epic 하나를 Release 하나로 본다.

| Agile 일반 | Version Moon |
|---|---|
| Product Vision | Charter(헌장) |
| Epic | Release(릴리스). 헌장의 큰 그림(Epic 목록)의 한 칸 |
| User Story | Issue 하나 |
| Acceptance Criteria | Issue 시작 점검의 "끝났다는 기준" |
| Definition of Ready (DoR) | Issue 시작 점검 |
| Definition of Done (DoD) | Issue 마무리 (PR 보고 + Retrospective) |
| PoC | Spike (따로 branch, merge 안 함, 결과는 결정 기록) |
| Sprint (고정 주기) | **없음**. Issue 하나씩, 필요할 때 Release Planning |
| Product Backlog | Backlog (Release Planning 때만, 최대 5개) |
| Retrospective | 회고 |
| Blocker | 막힌 일 |
| Risk Register | 위험 목록 |
