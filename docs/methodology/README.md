# 개발 방법론: Version Sun과 Version Moon

- 확정: 2026-11-14, Sun&Moon
- 상태: 후보. 아직 프로젝트에서 끝까지 써 보지 않았다. Version Sun은 SOUE002, Version Moon은 DEVP001에서 써 본 뒤 `specification/` 승격을 검토한다(00.common §2.3).

AI Agent와 함께 개발할 때의 진행 방식을 두 가지로 나눈다. 이 문서에는 두 방식에 공통인 원칙과 장치를 두고, 각 방식의 문서에는 그 방식에만 있는 것을 둔다.

| 문서 | 내용 |
|---|---|
| `README.md` (이 문서) | 방식 고르기, 공통 원칙, 공통 장치, 두 방식 비교 |
| [`version-sun.md`](version-sun.md) | 되돌리기 어려운 결정을 먼저 검증해 확정하고, MVP 범위 안에서 반복한다 |
| [`version-moon.md`](version-moon.md) | 헌장 하나로 목표와 끝을 정하고, Issue 하나씩 나아간다. 장치는 필요할 때 켠다 |

---

## 1. 방식 고르기

하나라도 해당하면 **Version Sun**, 모두 아니면 **Version Moon**으로 간다.

- [ ] 여러 시스템이 동시에 동작한다
- [ ] 먼저 확정해야 할 제약 조건이 있다 (예: 통신은 REST API만, 실시간은 WebSocket)
- [ ] 개발 전에 검증해야 할 것이 있다

## 2. 공통 원칙

### 2.1 서로 솔직하게
- **AI는 "다 했다"고 말하기 전에, 못 한 것과 틀렸을 수 있는 곳을 먼저 말한다.** 시키지 않아도 스스로 비판한다.
- **사람은 귀찮아도 결정하고, 건너뛸 때는 건너뛴다고 적는다.** 말없이 넘어가지 않는다.

비판적 검토를 사람이 매번 시켜야 하는 구조는 함정이 된다. 가장 지쳤을 때 가장 중요한 일을 기억해야 하기 때문이다. 그래서 AI의 자기 비판은 PR 보고의 기본 칸으로 둔다.

### 2.2 구멍이 소리치는 구조
구멍을 없앨 수는 없다. 대신 숨은 구멍을 보이게 하고, 결정될 때까지 계속 알리게 한다.

- AI는 빈칸과 가정을 스스로 메우지 않고 **결정 후보** 또는 **Issue**로 등록한다.
- 필요한 결정이 `decided`가 아니면 그 작업은 시작하지 않는다.
- 결정 대기, 막힌 일, 생략은 다섯 줄 확인과 계획에서 계속 보인다.

### 2.3 연속성은 저장소가 지킨다
AI Agent는 session이 바뀌면 잊는다. 연속성은 대화가 아니라 저장소의 문서와 기록이 지킨다. 요약은 만들지 않고, 원본은 한 곳에 두고 위치와 ID로 가리킨다.

## 3. 공통 장치

### 3.1 작업 요청 형식

```text
무엇을:     (이번 작업)
요구 목록:  (업무 규칙 ID)
지킬 것:    (기술 기준 ID)
하지 말 것: (범위 밖)
관련 결정:  (결정 ID)
끝나면:     PR 보고
```

### 3.2 PR 보고 (AI가 쓴다)
- [ ] 끝났다는 기준(또는 요구 ID)마다 결과와 근거. 근거는 실제 파일과 **실제로 실행한 test 명령과 그 결과**만 인정한다
- [ ] 확인하지 못한 것
- [ ] AI가 스스로 정한 가정
- [ ] 틀렸다면 어디서 틀렸을 것 같은가
- [ ] 요청 밖에서 바꾼 파일
- [ ] test 코드를 고쳤는가

### 3.3 결정 기록을 쓸 때
- AI는 초안을 쓰기 전에 기존 결정과 업무 규칙을 찾고, **"찾아본 기존 결정"**을 적는다.
- 기존 결정이나 업무 규칙을 바꾸면 **무엇을 바꾸는지**(결정 ID, 업무 규칙 ID)를 적는다.
- 결정 상태를 `decided`로 바꾸는 것은 사람만 한다.
- 결정이 다른 문서를 바꾸면 같은 PR에서 함께 고친다.

### 3.4 다섯 줄 확인 (새 session을 시작할 때)
새 session은 작업 전에 다섯 줄을 말하고 사람의 확인을 기다린다. 확인 전에는 아무것도 고치지 않는다.
1. 읽은 commit, 원격과 같은가
2. 현재 단계 또는 Issue와 상태 (근거 위치)
3. 켜져 있거나 진행 중인 것 (막힌 일, 위험 등)
4. 결정을 기다리는 것
5. 다음 할 일 (근거 위치)

사람은 근거가 없거나 이상한 줄을 본다. 이상하면 여기서 돌아간다. 마지막 PR에서 다시 읽고, 동작을 보고 이상하면 돌아간다.

### 3.5 막는 장치

| 막을 것 | 장치 |
|---|---|
| AI가 잠긴 계획(`docs/plan-baseline.md`)을 고친다 | `.claude/settings.json`의 `permissions.deny`로 수정을 막는다. 바꿀 때만 사람이 잠시 푼다 |
| 검증용 코드(PoC, 스파이크)가 본 코드로 들어간다 | 별도 branch에서 하고 merge하지 않는다. 결과는 결정 기록으로 남긴다 |
| 하지 말 것을 넘는다 | 파일 수정 승인 때 경로를 본다. PR에서 바뀐 파일 목록을 하지 말 것과 대조한다 |
| 오래된 문서로 시작한다 | 다섯 줄의 첫 줄에 읽은 commit을 적는다 |

### 3.6 공통 문서

| 문서 | 역할 |
|---|---|
| `docs/plan-baseline.md` | 잠기는 기준 계획 (헌장 등) |
| `docs/plan.md` | 진행 상황. merge 뒤에만 고친다 |
| `docs/journey.md` | 회고. 쌓아 간다 |
| `records/07.decision/` | 결정마다 파일 하나. 쌓아 간다 |
| `current-state.md` | 지금 유효한 규칙 |

## 4. 두 방식 비교

| | Version Sun | Version Moon |
|---|---|---|
| 핵심 | 시스템 사이의 약속과 제약 조건을 먼저 검증해 확정 | 안전장치를 체크리스트로 다시 세운 Agile |
| 맞는 곳 | 여러 시스템, 제약 조건, 검증 필요 | 시스템 하나, 모르는 것이 많음 |
| MVP | 관문에서 확정 | 헌장에서 첫 릴리스의 끝으로 정함 |
| 정리하는 시기 | 관문 (한 번) | 릴리스 계획 (필요할 때) |
| 장치 | 처음부터 둔다 | 필요할 때 켠다 |
| session 경계 | 단계 | Issue (회고 뒤) |
| 조심할 것 | 범위가 커지는 것 | 방향을 잃는 것 |
