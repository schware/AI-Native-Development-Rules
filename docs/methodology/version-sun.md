# Version Sun

- 확정: 2026-11-13, Sun&Moon
- 공통 원칙과 공통 장치(작업 요청 형식, PR 보고, 결정 기록 쓰는 법, 다섯 줄 확인, 막는 장치)는 [`README.md`](README.md)에 있다.

## 진행 전략
되돌리기 어려운 결정(시스템 사이의 약속, 제약 조건, 업무 규칙, 아키텍처)은 개발 전에 검증해 확정하고, 되돌리기 쉬운 결정은 개발하면서 정한다. 범위는 MVP로 고정하고 그 안에서 반복한다.

## 언제 Sun으로 가는가
- **여러 시스템이 동시에 동작하는 프로젝트**. 시스템 사이의 약속을 개발 전에 맞춰야 한다. 가장 중요한 기준이다. (예: BO, POS-SERVER, OMS-SERVER, POS, KIOSK, KDS, DID)
- 대규모이거나, 전체 그림을 먼저 맞춰야 하는 프로젝트
- **먼저 확정해야 할 제약 조건이 있는 프로젝트**. 업무를 몰라도 지켜야 할 조건이 정해져 있다. (예: "통신은 REST API만 쓴다", "실시간 알림은 WebSocket으로 한다")
- 개발 전에 검증해야 할 것이 있는 프로젝트

## 순서

```text
프로젝트 헌장 → 원칙 → 업무 범위 → 기술 기준 → 기술 검증 → MVP 범위 확정(관문) → 개발(Agile)
└──────────────── 위험 목록은 처음부터 끝까지 함께 간다 ────────────────┘
```

## 항목

| 항목 | 정하는 것 | 원본 문서 | 관문 뒤 | 왜 |
|---|---|---|---|---|
| **프로젝트 헌장** (Project Charter) | 프로젝트 ID, 프로젝트 이름, 제품 이름, 사업 배경, 제품 목표, 진행 방식, 책임자 | `docs/plan-baseline.md` | 잠김 | 모든 결정의 출발점 |
| **원칙** (Principles) | 결정이 갈릴 때 고르는 문장. 지속 가능성 기준(10년 유지, 지속 가능, 확장성) | `docs/plan-baseline.md` | 잠김 | 기준이 흔들리면 모든 결정이 흔들린다 |
| **업무 범위** (Business Scope) | 담당 업무, 하지 않는 것, 업무 규칙 ID | 업무 범위 문서 | 큰 틀 잠김 | 세부는 개발하며 정한다 |
| **기술 기준** (Architecture & Engineering Standards) | 시스템 구성과 시스템 사이의 약속(API, 전문, 데이터 흐름), 제약 조건, 통신, 언어, DB, 설계서의 큰 틀, 기준 ID | 기술 기준 문서 | 큰 틀 잠김 | 시스템 사이의 약속이 바뀌면 모든 시스템이 흔들린다 |
| **기술 검증** (PoC) | 확인할 질문, 끝나는 기준, 기간, 결과 | 결정 기록 | 닫힘 | 넓히면 개발을 위한 개발, 설계를 위한 설계가 된다 |
| **MVP 범위** (MVP Scope) | 최소 기능, MVP 이후 목록 | `docs/plan-baseline.md` | 잠김 | 넓히면 끝없는 확장이 되고 욕심이 된다 |
| **위험 목록** (Risk Register) | 위험, 판단, 다시 볼 시점 | 위험 목록 문서 | 계속 | AI에게 "다 해 주세요"가 되지 않기 위해 |

### 항목별로 지킬 것
- **프로젝트 헌장**: 프로젝트 ID와 이름의 원본은 `project.yaml`이다. 제품 목표는 "누구를 위해, 무엇을 만들어, 어떤 문제를 푸는가" 한 문장으로 쓴다. 한 프로젝트에서 제품이 여러 개일 수 있다.
- **원칙**: 결정을 실제로 고를 수 있는 문장이 될 때까지 AI와 다듬는다. 보이고 확정되어야 하는 문장이다.
- **업무 범위**: 하지 않는 것을 반드시 적는다.
- **기술 기준**: 시스템 사이의 약속과 제약 조건을 먼저 정한다. 제약 조건마다 왜 정해졌는지(회사 규정, 기존 시스템 등)를 결정 기록으로 남긴다. 라이브러리, 폴더 구조, 화면 배치 같은 세부는 개발하면서 정한다.
- **기술 검증**: 시스템 사이의 약속이 실제로 동작하는지를 먼저 확인한다(예: 주문 하나가 KIOSK에서 DID까지 통과). 시작할 때 확인할 질문, 끝나는 기준, 기간을 정한다. 별도 branch에서 하고 main에 merge하지 않는다. 결과는 결정 기록 하나로 남기고 닫는다.
- **MVP 범위**: 기술 검증이 끝난 뒤 확정한다. 새 생각은 버리지 않고 MVP 이후 목록에 적는다.
- **위험 목록**: 위험마다 사람이 **받아들인다, 대응한다, 나중에 본다** 중 하나로 정한다. "나중에 본다"는 다시 볼 시점을 함께 적는다. AI에게 비판적 검토를 계속 요청하되 같은 위험을 다시 묻지 않는다.

## 동시 개발 준비 (관문 뒤)

여러 시스템을 AI session 여러 개로 동시에 만드는 방법이다. AI session끼리는 서로 말을 하지 못한다. 그래서 **확정된 약속이 session 사이의 대화를 대신한다.**

### 언제 동시에 시키나
- **관문 전에는 동시에 시키지 않는다.** 약속을 정하는 동안 여러 session을 돌리면, 각자 다른 약속을 상상해 설계가 여러 갈래가 된다. 약속은 한 session에서 하나로 정한다.
- **관문 뒤에는 동시에 시킬 수 있다.** 약속에 없는 것이 필요해지면 혼자 정하지 않고 멈춘다.
- **처음에는 둘부터.** AI가 늘어도 검토하고 결정하는 사람은 하나다. 감당할 수 있는 양을 재 보고 늘린다.

### 나누는 법
- **시스템별로 나눈다.** 예: BO / POS·KIOSK / KDS·DID·KDS Server / POS-Server / OMS-Server / App-Server.
- session마다 **자기 worktree와 자기 폴더**만 쓴다. 예: POS-Server session은 `src/pos-server/`만 고친다.
- 함께 쓰는 파일(`docs/plan.md`, 결정 기록 번호, 공통 설정, 의존성 파일)은 **한 곳(상위 session 또는 Sun&Moon)에서만** 고친다. 하위 session은 제안만 한다.
- branch는 Issue 하나에 하나, main에서만 딴다. branch 위에 branch를 쌓지 않는다.

### 약속 지키기
- **약속 test (Contract Test)**: 확정된 API 명세대로 주고받는지 CI가 PR마다 확인한다. 사람이 보기 전에 기계가 먼저 어긋남을 잡는다.
- **하위 호환 (Backward Compatibility)**
  - **더하는 변경**(새 칸을 선택 항목으로 추가): 아무도 멈추지 않는다. 결정 기록만 남긴다.
  - **바꾸거나 빼는 변경**(칸 이름 변경, 필수 칸 추가, 칸 삭제): 그 약속을 쓰는 session만 멈추고 결정을 기다린다.
- **다음 Client가 올 자리를 비워 둔다.** 예: 주문 약속에 주문 경로(채널) 칸을 두어 KIOSK, POS, 나중의 App을 구분한다. 그러면 App은 새 Client 하나를 더하는 일이 된다.

### 관문 도달 조건
관문 G1에서 함께 정하고 잠근다. 개발 중에 조건을 낮추지 않는다. 낮춰야 하면 결정 기록을 남긴다. 도달은 "거의 됐습니다"가 아니라 조건마다 근거(test 결과, merge된 PR)로 선언한다.

| 관문 | 도달 조건 | 넘겨주는 것 | 받는 쪽 |
|---|---|---|---|
| **G1. 약속 확정** | API와 전문 확정, 약속 test 작성, 기술 검증(주문 하나가 KIOSK에서 DID까지) 통과 | 잠긴 API 명세, 약속 test | 모든 시스템 |
| **G2. 시스템 완료** (시스템마다) | 자기 Issue 모두 merge, 약속 test 통과, mock 없이 연결 가능, 알려진 Bug 목록 정리 | 동작하는 시스템, 남은 Bug 목록 | 통합 test |
| **G3. 통합 완료** | 정해 둔 업무 흐름(예: 주문, 결제, 조리·호출, 매출)이 처음부터 끝까지 흐른다 | 통합 test 결과 | QA |
| **G4. QA 완료** | 업무 규칙 ID마다 Scenario 확인, 남은 Bug는 "고친다 / Release 뒤로 / 받아들인다" 중 하나로 결정 | QA 결과, 결정 기록 | Release |

### 시스템 사이의 도달 조건
동시에 만들어도 기대는 쪽이 먼저 도달해야 하는 조건이 있다. 관문 G1에서 적어 둔다. 이 줄이 전체 기간을 정하는 가장 긴 줄(Critical Path)이다.

| 먼저 도달할 쪽 (예) | 조건 | 그래야 시작할 수 있는 쪽 |
|---|---|---|
| POS-Server | 주문 API가 약속 test를 통과하고 실제로 응답한다 | POS·KIOSK의 실제 연결 |
| OMS-Server | 주문을 받아 KDS Server로 넘긴다 | KDS·DID의 실제 연결 |
| App-Server | 주문 API를 App 채널로 받는다 | App (MVP 이후) |

### 서로 알리기
**전체 지도**: 상위 저장소에 한 장으로 둔다. 하위 session은 Five-line Check 때 읽는다.

| 시스템 | 범위 (한 줄) | 지금 관문 | 기대는 쪽 | 받는 쪽 |
|---|---|---|---|---|

**상태 신호**: 하위 session은 Issue를 시작할 때, 끝낼 때, 막혔을 때 상위에 상태 하나를 남긴다.

| 상태 | 뜻 | 함께 적을 것 |
|---|---|---|
| **진행** | 일하고 있다. 상대가 아직 없어도 약속이 있으면 mock으로 진행한다 | 지금 Issue |
| **결정 필요** | 약속에 없거나 약속이 바뀌는 중이다. mock조차 만들 수 없다 | Decision Candidate 번호 |
| **대기** | 내 쪽은 끝났고, 상대가 도달해야 실제 연결을 확인할 수 있다 | 어느 시스템의 어떤 도달 조건 |
| **할 일 없음** | 업무 지시가 없다 | 마지막으로 끝낸 Issue |
| **도달** | 관문 도달 조건을 채웠다 | 근거 (test 결과, merge된 PR) |

- **약속에 없으면 mock을 지어내지 않는다.** 결정 필요로 멈춘다. AI는 핑계를 대는 대신 빈칸을 지어내서 계속 가기 때문이다.
- **할 일이 없으면 일을 지어내지 않는다.** 상태를 남기고 멈춘다. 기다리는 동안 해도 되는 일(mock으로 test 보강, 자기 시스템의 Bug)은 미리 정해 둔 것만 한다.
- **관제**: 상위 session이 상태를 모아 Sun&Moon에게 보여 준다. 업무 지시는 Sun&Moon이 정하고, 상위 session은 전달만 한다.

### 묶기: 통합 test와 QA
마지막에 통합 test와 QA로 전체를 묶는다. 기술 검증(G1)으로 통합의 뼈대를 먼저 세우고, 약속 test로 계속 맞춰 왔으므로, 마지막은 "처음 합쳐 보는 날"이 아니라 "맞춰 온 것을 최종 확인하는 날"이다.

| | 통합 test | QA |
|---|---|---|
| 확인하는 것 | 시스템끼리 이어져 동작하는가 | 업무 규칙대로 동작하는가 |
| 기준 | 시스템 사이의 약속 | 업무 범위의 업무 규칙 ID |
| 누가 | 기계 (자동 test) | 사람 (Scenario 목록) |
| 예 | 주문이 POS-Server에서 OMS-Server를 거쳐 KDS에 뜬다 | 승인 응답이 없으면 망취소 후 결제 화면으로 돌아간다 |

## session
- session은 단계 경계에서 바꾼다.
- 새 session은 [`README.md`](README.md) 3.4의 다섯 줄 확인을 한다. 사람은 `docs/plan.md`, `docs/plan-baseline.md`와 대조한다.

## 뒤로 가는 경우
- **작은 변경**: 업무 규칙 하나, 기술 세부 하나가 바뀐다. 변경 결정을 남기고 해당 부분만 고친 뒤 계속 간다.
- **관문 다시 열기**: 제품 목표나 원칙이 흔들리거나, 시스템 사이의 약속이나 제약 조건이 바뀌거나, MVP 범위로 목표를 이룰 수 없다고 드러난다. `docs/plan-baseline.md`부터 다시 본다.
- 둘을 가르는 것은 사람의 판단이다. 결정 기록과 다섯 줄 확인이 그 판단을 돕는다. 조용히 되돌아가지 않고, 다시 열 때는 "관문을 다시 연다"는 결정을 남긴다.
