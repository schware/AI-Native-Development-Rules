# KEDP에서 배운 것: AI Native Development 다음 버전을 위한 정리

2026-10-25 · KEDP001(한국 경제 데이터 플랫폼)을 시작하며 겪은 일

## 목적

KEDP001을 실제로 시작하면서 "사람이 결정한 것을 AI Agent가 실행하게 만드는 과정"에서 부딪힌 일과 배운 점을 정리한다. AI Native Development의 다음 버전, 특히 8번 명세 대상(확정된 결정을 현재 규칙과 실행 가능한 작업으로 전환하는 방법)에 반영할 재료다.

---

## 1. 핵심: 사람이 생각한 것을 남겨야 Agent가 그대로 만든다

### 있었던 일

"웹페이지를 만들어 달라"고 요청하려는 순간, 화면 도구, 데이터 출처, 범위가 정해져 있지 않았다. 그대로 요청하면 Agent가 대신 고르게 된다.

### 배운 점

사람이 생각한 것을 **종류에 맞는 자리에** 남기면, Agent는 그것을 보고 "이렇게 하는구나" 하고 만든다. 남기지 않은 것은 Agent가 짐작한다.

| 사람이 생각하는 것 | 남기는 곳 | Agent는 |
| --- | --- | --- |
| 왜 이렇게 하나 (여러 방법 중 고른 이유) | 결정 기록 (`records/.../D0xx`) | 근거로 읽음 |
| 무엇을 만드나 (모양, 화면, 데이터) | 명세 (`specification/`) | 그대로 만듦 |
| 항상 지킬 것 | Agent 규칙 (`.claude/`) | 매번 지킴 |
| 이번에 할 일과 끝난 기준 | Issue | 그 일만 하고 기준을 확인 |
| 따라 하는 방법, 지난 기록 | 안내서·참고 (`docs/`) | 필요할 때 찾아 읽음 |
| 실제 응답, 조사 자료 | 근거 (`samples/`) | 테스트와 설계의 바탕 |

### 프레임워크에 넣을 것

- 위 표를 **문서 종류와 위치의 표준**으로 정의한다.
- **착수 조건**: 작업을 요청하기 전에, 그 작업에 필요한 결정이 모두 `decided`인지 확인한다. 미정이 있으면 요청하지 않는다.

## 2. 모든 것을 결정 기록으로 만들지 않는다

### 있었던 일

결정 기록을 하나씩 만들다 보니 "이것도 D로 남겨야 하나?"가 반복됐다.

### 배운 점

D가 너무 많아지면 사람도 Agent도 읽기 어렵다.

| D로 남기는 것 | D로 남기지 않는 것 |
| --- | --- |
| 여러 방법 중 하나를 고를 때 | 함수 이름, 파일 안의 세부 배치 |
| 되돌리기 어려울 때 | 한 번 쓰고 끝나는 작은 선택 |
| 여러 Agent가 알아야 할 때 | Agent가 규칙 안에서 정해도 되는 것 (결과 보고에 적게 함) |

### 프레임워크에 넣을 것

- D로 남기는 기준과, Agent가 스스로 정해도 되는 범위를 함께 정의한다.

---

## 3. Agent에게 시키는 말은 정확해야 한다

### 있었던 일

"Go를 만들기 전에 REST API용 모듈을 먼저 만들어야 한다"는 생각을 정리하다 보니, "REST API 모듈"이 두 가지로 읽혔다.

- (가) 외부 API(ECOS·KOSIS)를 **부르는** 모듈
- (나) 우리 화면에 데이터를 **주는** REST API

### 배운 점

사람은 문맥으로 알아듣지만, Agent는 애매한 말을 자기 식으로 해석한다. 그래서 결정 기록에 **용어 정의**를 넣었다("수집 모듈"과 "조회 API").

### 프레임워크에 넣을 것

- 결정 기록과 명세에 **용어** 칸을 둔다. 같은 말이 두 가지로 읽힐 수 있으면 이름을 나눈다.

## 4. 첫 구현이 나머지의 설계도가 된다

### 있었던 일

"제공처 세 곳(ECOS, KOSIS, 공공데이터포털)을 붙일 때 공통 모듈을 먼저 만들까, 하나씩 붙이고 나중에 합칠까"를 비판적으로 따져 봤다.

1. 공통 모듈을 먼저 만들자 → 그런데 제공처마다 규칙이 달라서 실제로 붙여 보기 전에는 공통을 알 수 없다.
2. 세 개를 따로 만든 뒤 마지막에 합치자 → 그런데 동작하는 코드 세 개를 한꺼번에 고쳐야 해서 실수가 늘고 확인할 양이 커진다.
3. 결론: **확실히 같은 것만 처음부터 공통으로 두고, 하나씩 붙일 때마다 겹치는 부분을 찾아 그 자리에서 공통으로 뺀다.** 앞의 것도 바로 고친다. 마지막에 한꺼번에 합치는 단계는 없다.

### 배운 점

- **Agent는 처음 만든 코드를 본보기로 따라 한다.** 첫 구현에 틀이 없으면 다음 것도 그 모양을 베낀다.
- "세 번 보고 공통으로 만든다"는 원칙은 맞지만, **키 가리기처럼 확실히 같은 것은 처음부터** 공통이어야 한다.
- 고칠 때마다 망가지지 않았는지 확인하는 장치가 필요하다. **받아 둔 실제 응답 샘플로 테스트**를 만들어 안전망으로 쓴다.
- "붙인다"에도 깊이가 있다. **샘플 확보**(빨리, 전부)와 **기능 완성**(하나씩)을 나눈다.

### 프레임워크에 넣을 것

- 반복되는 구조를 만들 때의 원칙: "확실한 공통은 먼저, 불확실한 공통은 실제로 붙여 보며, 고칠 때마다 테스트로 확인".
- 실행 계획에 "근거 확보"와 "기능 완성"을 다른 단계로 둔다.

## 5. 실행 작업(Issue)은 세 칸이면 된다

### 있었던 일

Agent에게 일을 시키기 전에 Issue를 쓰는 것이 생각보다 어려웠다. "이것까지 다 써야 하나?"가 나왔다.

### 배운 점

| 칸 | 왜 필요한가 |
| --- | --- |
| 할 일 | Agent가 **무엇을** 만들지 |
| 끝났다는 기준 | Agent가 **언제 멈출지**, 사람이 **무엇을 확인할지** |
| 하지 말 것 | Agent가 **범위를 넘지 않게** |

- 역할과 근거는 규칙 파일과 결정 기록에 이미 있으면 짧게 줄여도 된다.
- **Issue가 짧고 분명할수록 Agent가 덜 헤매서 토큰을 덜 쓴다.** 토큰이 많이 드는 경우는 할 일이 애매할 때, 끝나는 기준이 없을 때, 하지 말 것이 없을 때다.
- Issue를 잘 쓰는 것이 곧 PM이 팀을 움직이는 연습이다. (Jira로 하려던 연습도 이것이었다.)

### 프레임워크에 넣을 것

- 실행 작업의 **표준 모양**(세 칸)을 정의한다.
- 저장소에 **Issue 양식 파일**(`.github/ISSUE_TEMPLATE/`)을 두어 매번 같은 칸으로 시작하게 한다.

## 6. 기록이 저장소에 있어야 다른 Agent가 안다

### 있었던 일

Windows의 Claude(상의, 문서)와 Linux 개발 서버의 Claude Code(개발)는 기억을 공유하지 않는다. 대화에서 합의한 내용을 `.claude/`와 결정 기록에 넣어 GitHub에 올린 뒤에야 Linux 쪽이 알았다. 또 이전 PR이 merge되지 않은 채 다음 작업을 쌓아 순서가 꼬인 일도 있었다.

### 배운 점

- Agent끼리는 **저장소 문서로만** 맥락을 넘긴다.
- 순서: **정한다 → 기록해서 올린다(merge까지) → 일을 시킨다.** 기록이 main에 들어가기 전에 일을 시키면 Agent는 그 기록을 모른다.
- 새 작업을 시작하기 전에 이전 PR이 merge됐는지 확인한다.

### 프레임워크에 넣을 것

- "저장소에 기록된 것만 결정으로 인정한다"를 **Agent 사이의 전달**까지 넓힌다.
- 작업 흐름에 "기록 merge 확인" 단계를 넣는다.

## 7. 사람과 Agent가 일하는 방식

### 있었던 일과 배운 점

| 있었던 일 | 정리된 방식 |
| --- | --- |
| "~하죠"라는 말을 실행 지시로 받아 Agent가 바로 명령을 실행하려다 멈춤 | 말은 방향을 꺼내는 것이다. 실행은 할 일을 보여 주고 허락받은 뒤 한다. 누가 실행할지 애매하면 명령만 안내한다. |
| "결정 기록으로 남기세요"라고만 안내해 사람이 모든 문서를 찾아봐야 했음 | Agent가 직접 고치거나, 최소한 "어느 파일의 어느 부분을 이렇게"까지 알려 준다. |
| 정리된 긴 목록을 받으니 무엇을 원하는지 다시 고민해야 했음 | 항목마다 추천을 붙여 "예/아니오"로 답할 수 있게 묻는다. |
| MVP 중에 "서버가 멈추면?" → "그럼 확인 서버가 멈추면?" 같은 끝없는 질문 | MVP에서는 "멈추면 멈춘다, 대비는 MVP 이후"로 둔다. |
| Agent에게 보낼 요청문 초안이 반말이었음 | 요청문은 존댓말로 쓴다. 사람이 그대로 붙여 넣기 때문이다. |
| 콘솔에서 Issue 설명을 쓰기 어려웠음 | 설명 쓰기와 merge는 GitHub 웹, 저장·올리기는 콘솔로 나눈다. |
| 맡기는 범위를 어디까지 할지 | 처음에는 Agent가 작업, 사람이 commit·merge. **서로 믿음이 쌓이면** 맡기는 범위를 넓힌다. |

### 프레임워크에 넣을 것

- **위임 수준**을 단계로 정의한다(안내만 → 작업까지 → PR까지 → merge까지)와 다음 단계로 넘어가는 조건.
- 사람에게 무엇을 묻는 방식의 기준(추천 붙이기, 정확한 파일 안내, 한 번에 하나).

## 8. 도구와 범위를 고르는 기준

### 있었던 일

- **Jira**: 연결할 곳(Jira 앱, GitHub 앱, 자동 규칙, MCP)이 많아 사람 일이 늘었다. GitHub 쪽 연결이 빠진 것을 늦게 알았다. 결국 GitHub Issues로 바꿨다(merge하면 `Closes #번호`로 자동 종료).
- **관리자 화면에서 API 키 입력**: 웹에서 키를 받는 순간 보안 설계가 훨씬 커진다. MVP에서는 화면은 상태만 보여 주고 키는 서버 `.env`에서만 관리하기로 했다.
- **지표 비교**: 비교를 넣으면 분석이 필요하고, 분석에는 AI Agent와 큰 작업이 필요하다. MVP에서 빼고 2차로 미뤘다.
- **지표 설정**: 주기, 기간, 관련 지표 같은 값은 코드에 고정하지 않고 관리자 화면(DB)에 두어 나중에 다시 보고 고칠 수 있게 했다.

### 배운 점

- 새 도구는 **연결 비용 vs 얻는 것**을 따지고, 기본 도구(저장소 내장 기능)를 먼저 쓴다.
- MVP는 "먼저 수집한다, 먼저 저장한다, 먼저 보여준다, 해석은 그다음"으로 단순하게 끝낸다.
- 비밀값은 MVP에서 웹 화면으로 받지 않는다.
- 나중에 바뀔 값은 코드가 아니라 설정으로 둔다.

### 프레임워크에 넣을 것

- 5번 명세 대상(기회 선택과 평가)에 도구 도입 기준과 MVP 범위를 줄이는 기준을 넣는다.

## 9. 같은 문제가 두 번 나면 기록한다

### 반복된 문제

| 증상 | 원인 |
| --- | --- |
| commit했는데 PR이 "차이 없음"으로 실패 | `git add`를 빠뜨림 |
| merge 명령이 "PR이 없다"고 함 | PR 만들기를 건너뜀 |
| commit 때 "gitleaks가 없다" | 설치 전에 열린 터미널을 씀 |
| `gh` 명령 뒤 이름·비밀번호를 물음 | gh가 덧붙이는 경로의 역슬래시 문제 |
| 새 규칙을 Agent가 모름 | 규칙은 시작할 때만 읽음 (Agent를 다시 켜야 함) |

### 프레임워크에 넣을 것

- "같은 문제가 두 번 이상 발생하면 문서를 추가한다"를 실제로 운영하는 방법: 안내서마다 **"막히면" 표**를 두고 모은다.

## 요약: 다음 버전에 넣을 우선순위

1. **착수 조건**: 필요한 결정이 `decided`일 때만 작업을 요청한다.
2. **실행 작업의 세 칸**: 할 일, 끝났다는 기준, 하지 말 것 (+ Issue 양식 파일)
3. **문서 종류와 위치의 표준**: 결정, 명세, 규칙, 작업, 안내서, 근거
4. **D로 남기는 기준**과 Agent가 스스로 정해도 되는 범위
5. **용어 정의 칸**: 애매한 말을 나눠 부른다.
6. **반복 구조의 원칙**: 확실한 공통은 먼저, 나머지는 붙여 보며, 고칠 때마다 테스트
7. **Agent 사이의 전달**: 저장소 문서로만, merge 확인 후 작업 요청
8. **위임 수준의 단계**와 사람에게 묻는 방식
